Install

git clone https://github.com/e6qu/fun-refactor
cargo install --path fun-refactor   # installs `fr`

Rust 2021 edition and a C compiler — every tree-sitter grammar is C, so a cold build takes a few minutes.

Naming a target

Commands that act on a symbol take a target, written one of two ways.

FormWhenExample
path:line:col Always works. 1-based; must land on the identifier itself, at the definition or any use of it. fr refs pkg/action/action.go:725:6
a bare name When the name is unique in the workspace. Otherwise the tool lists the candidates and stops. fr callers RunAll
path:l:c-l:c fr extract, which acts on a range rather than a symbol. fr extract a.go:8:5-8:19 count
path fr imports, and the destination argument of fr move. fr imports pkg/action/install.go

Relative paths are read against the workspace root — the current directory unless -C says otherwise — not against your shell's working directory. A path that does not exist is an error that says where it looked.

If you are not sure what to write, the playground shows the path:line:col of whatever the cursor is on, in its status bar, and copies it when clicked. It is the same string this table describes, so you can point at something in the browser and act on it in a terminal.

Confidence

Every resolved reference carries the rule that resolved it. This is the tool's central idea: it would rather hand you a list to check than change a line it cannot justify.

TierWhat proved itRewritten
exact The lexical scope chain, the same file, or the enclosing package. yes
import-qualified An import binding in this file names the file it came from. yes
field-based The name is a member of something, but the receiver's type is not tracked. no — reported
name-only Nothing but the name matched. no — reported

Refactorings also report textual occurrences — the name in a string or a comment — and parse errors, because a file that could not be read may hold references nobody can see.

Changing

All of these print a diff and write nothing until --write.

fr renameRename a symbol and everything that points at it
fr extractAn expression into a binding, or statements into a function
fr inlineThe reverse of either
fr signatureAdd, remove or reorder parameters, updating every call
fr moveMove a symbol to another file, carrying its imports
fr deleteDelete it, refusing while anything uses it
fr importsDrop unused imports and sort the rest
fr rewriteLocal transformations: invert-if, guard-clause, de-morgan
fr restructurePattern rewriting: old($X) → new($X)
fr remove-flagRetire a feature flag and the branch that served it
fr translateWrite the file as another language, or port a route to FastAPI

--json works on every command. fr capabilities prints the full matrix of what each language supports, with the reason attached to every cell that is not supported.

Writing a file as another language

fr translate has three modes, and they make three quite different promises. Run it without a target to see which apply to a file, each with the reason the others do not.

ModeWhat you getExample
Containment The same bytes under a different grammar. Nothing is rewritten, so nothing can be lost. fr translate app.css scss
Translation A draft between Rust, Go, Python and TypeScript. Signatures carry exactly; anything with no counterpart is in the output verbatim as a comment, and counted. fr translate sensors.py typescript
Framework port A Next.js API route as a FastAPI module — routes, methods, path parameters, models and bodies. fr translate 'app/api/users/[id]/route.ts' fastapi

The signature is the contract. Every parameter, in order, with its type and the return type, carried exactly — only the spelling changes. Where a type has no counterpart it is written through by name and counted, because quietly substituting a type is how a signature stops meaning what it said.

Names take the target's convention

TypeScript writes userName, Python writes user_name, Go says "exported" with a capital letter. A translated file adopts the target's convention, under the same rule the refactorings follow: rename what the file declares and nothing else. Functions, records, fields, constants, parameters and locals are re-spelled at their declaration and at every use. A name the module does not declare — db.users.find, a library function — is left exactly as written, because re-casing it would rename somebody else's API.

Typed Python and typed TypeScript

The closest pair gets the closest translation: list[str] is string[], dict[str, int] is Record<string, number>, Optional[T] is T | null, a @dataclass is an interface, an f-string is a template literal, and [f(x) for x in xs if p(x)] is xs.filter(p).map(f). Both directions carry zero constructs verbatim — the strongest claim any pair in this tool makes.

Next.js to FastAPI

A Next.js API route cannot be translated by reading the file alone, because the URL is the path. app/api/users/[id]/route.ts serves /users/{id} and nothing inside the file says so; [...path] is a catch-all, which FastAPI spells {path:path} and which a translation emitting {path} would silently point at the wrong URLs.

Next.jsFastAPI
export async function GET@router.get(…) on an async def
an exported interfacea Pydantic BaseModel
NextRequestRequest — same headers, same await .json()
const id = context.params.iddropped — FastAPI already supplies it
return NextResponse.json(x)return x
NextResponse.json(x, { status: 404 })JSONResponse(x, 404)

It refuses a .tsx file containing JSX, and says why: a React component renders a user interface and a FastAPI endpoint answers HTTP. There is no translation between them, and a file that pretended there was would be worse than no file. What stays foreign is your own dependencies — the database calls and helpers the route imported — which no translation could supply.

In the playground this is the Rewrite button, which lists every target with what it would cost, grouped by which of the three promises it makes.

Measured against real projects

A fixture is written by whoever writes the assertion. So the same translations run over two MIT-licensed projects vendored unmodified and pinned — fastapi/full-stack-fastapi-template and shadcn-ui/taxonomy — asserting three properties rather than exact output: it parses as what it claims to be, it adopts the target's conventions, and nothing goes missing quietly.

That found what the fixture tests did not, including two silent wrong answers: session?.user.id became None.id, and params.postId as string became None. Both are now carried with the original. On the hardest route in the corpus the count of constructs carried over as comments went from 15 to 3.

API contracts

A refactoring preserves behaviour. A translation preserves a signature. Rewriting a service in another language has to preserve something else again — the only thing anyone outside the repository can see: the contract. A caller does not import your functions. It sends PATCH /posts/42 and expects 204.

That makes it a strange kind of cross-language refactoring: the language, the framework, the internal structure and every function signature are all free to change, and the six things below are not.

Contract elementWhere it lives in Next.jsCarried?
URL templatethe file pathyes
Catch-all segment[...path]yes — as {path:path}
Methodthe exported function's nameyes
Path parametersthe bracketed segmentyes, typed
Request body schemaa zod schema, or an interfaceonly from an interface
Response body schemausually nowhereno
Status codesthe returned objectinto the code, not the contract

The URL is the path

app/api/posts/[postId]/route.ts serves /posts/{post_id}, and nothing inside the file says so. No content-only translation can recover that, however well it reads TypeScript. It is the one part of the job that needs the tree rather than the text, and it is most of the value.

[...path] is a catch-all — it matches across slashes, which FastAPI spells {path:path}. A translation emitting {path} would answer a strictly smaller set of URLs than the service it replaced, silently, and only for the requests with a slash in them.

Why OpenAPI makes the two directions asymmetric

FastAPI derives OpenAPI from the code — the decorator gives the URL and method, the annotated parameters give the path parameters, a Pydantic model gives the body schema. The contract is a projection of the types rather than a document somebody maintains. Next.js has no built-in equivalent.

So Next.js → FastAPI gains a machine-readable contract where none existed — and that is the trap. The generated OpenAPI is exactly as complete as what carried across, and it does not look incomplete.

Right behaviour, wrong document

The sharp edge, and the tool now reports it. A translated handler returns 204 and behaves correctly, but FastAPI builds its OpenAPI from the decorator — so a status on a returned Response changes what the endpoint does without changing what it says it does: 

@router.delete("/posts/{post_id}")          # documents 200
async def delete(post_id: str, req: Request):
    return Response(status_code=204)        # returns 204

The rewrite is behaviour-preserving and contract-shrinking at once, and every test you have will pass. The tool does not add status_code= to the decorator, because which status is the success one is a judgement about the endpoint rather than a fact about the syntax. It lists every status it saw and says what will happen if you leave them where they are.

How you would actually check a rewrite

The tool preserves what it can see and reports the rest. It does not verify the contract, and no amount of reading one side can: export the contract before, rewrite, export /openapi.json after, and diff them — treating every difference as a defect until argued otherwise. Emitting that baseline from the route tree is a real gap, and it is written down as one.

The playground

The playground is this analysis compiled to WebAssembly. There is no server: the tab fetches a public repository from GitHub, holds it in memory, indexes it, and every answer and every edit happens in the browser. Nothing is uploaded and nothing on GitHub changes — the diff is the artifact, and you can download the session as a patch.

It ships all twenty-nine capabilities and a bundled fifteen-language workspace, so every one of them can be tried against every grammar without waiting for a download or being rate-limited. Ten preset repositories cover the same ground on real code.

PaneWhat it is for
Files Every file loaded. A file in a language this build has no grammar for is listed and reported, not silently dropped.
Outline Every definition in the open file, from the index — the same answer fr symbols gives.
Structure The parse tree. Every answer the tool gives is a claim about this tree, so a surprising answer usually becomes obvious here — whether a name is an identifier or a field_identifier decides what half the tool will do with it. Clicking a node selects exactly the bytes it covers, which is how you pick a range for extract.
Status bar The coordinate, the symbol under the cursor, whether it is exported, where it is defined, and the innermost tree node.
Result What the action returned — a diff, a list with confidence tiers, a call tree, or the refusal and its reason. A refusal is an answer: it names the rule that stopped the change.

Navigation is where an editor keeps it: F12 or ⌘/Ctrl-click goes to the definition, the arrows in the bar walk back and forward through the jumps you made, and a right-click offers every action that applies to what is under the cursor — with a reason on each one that cannot run. The columns drag, the sidebar sections fold, and the layout is remembered.

What the browser cannot do is what needs a filesystem: there is no fact cache, and a repository has to be small enough to hold in a tab, so the loader caps the file count and says what it left out.

Asking the page instead of reading it

The playground answers to something other than a person too. A query parameter picks the rendering, and the two machine-readable ones never load the editor — about seven kilobytes of JavaScript rather than four megabytes.

URLWhat comes back
playground/ The page. Same as ?render_as=html.
playground/?render_as=json The same interface described rather than drawn: the panes and what is in them, the toolbar, and every action with whether it can run and why not.
playground/?render_as=json_data The analysis with no interface around it — what was indexed, the entry points, the call graph, the dead code, the duplicates, and the open file's symbols and parse tree.
&repo=psf/requests Which workspace to answer about. repo=sample uses the bundled fifteen-language one.
&file=src/requests/api.py Which file the answer is about.

The whole document body is the JSON, so JSON.parse(document.body.textContent) is the contract. An unknown render_as is refused with the list of valid ones rather than quietly treated as HTML.

How it works

Parsing, and where the trees live

Each file is parsed by tree-sitter, one grammar per language, into a tree that keeps every byte — comments and whitespace included. That is what makes losslessness possible: an edit is a byte-range splice, so everything outside the range is untouched by construction.

The trees are not stored. They live for the duration of one file's extraction and are dropped; what survives is a much smaller set of facts — symbols, references, scopes, imports — each carrying a byte span. Keeping 16,000 syntax trees in memory would cost more than re-parsing the few files any one command needs.

Positions are byte offsets everywhere except the command line. Line and column are a display format, and a tool that miscounts a column corrupts a file.

Helm gets one extra step. A template action is masked before parsing — replaced by filler of exactly the same byte length — so the surrounding YAML still has valid structure and every offset stays correct. The actions are then parsed separately, which is how .Values.image.tag becomes a reference to a values key that a rename can rewrite.

The cache

Content-addressed. A file's facts are keyed by the SHA-256 of its contents combined with a fingerprint of the query set that produced them. Change the file and the key changes; change a query and every key changes. There is no invalidation logic to get wrong, because there is nothing to invalidate — a stale entry is simply never looked up. 

fr cache
location  ~/Library/Caches/fun-refactor/v2-dbe4d237fed430ca
size      3791 KiB

fr cache --clear
fr <command> --no-cache

Set FUN_REFACTOR_CACHE to override the location. The directory name carries a schema version, so a release that changes what a fact is starts a new namespace rather than reading old data with a new meaning.

The edit engine

Every refactoring returns a plan and touches nothing. The engine then:

  1. Rejects overlaps. Two edits to the same bytes are a bug in the caller, not something to resolve by picking one.
  2. Applies in descending offset order, so earlier offsets stay valid as it goes.
  3. Reparses every changed file and refuses the whole edit if the file parses cleanly now and would not afterwards.
  4. Commits atomically. Either every file is written or none is.

That reparse check is the net, not the safety. It cannot catch a change that parses and means something else — hoisting a statement out from under the condition that guarded it, or dropping the brackets a de Morgan result needs. Those are caught by the analysis being right, which is why the confidence tiers exist and why the tool refuses as much as it does.

Known limitations

BUGS.md lists every one, each with the measurement that established it. In summary: reachability under dynamic dispatch is undecidable from source and is reported rather than guessed; Helm values passed on a command line are invisible to a workspace scan unless you supply them with -f and --set; CSS classes named inside TSX helper calls are not resolved, which measurably costs about two-thirds of the reach of a stylesheet rename in a modern React codebase; and two upstream grammar gaps, in SCSS and in Go's handling of a user-defined new.
