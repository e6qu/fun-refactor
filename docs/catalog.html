The catalogue

Fowler and Beck, worked in Python

A refactoring is a change to the text of a program that leaves what the program does alone. That is the whole definition, and it is the only thing every entry here has in common — so every entry says, in its own words, what stayed the same.

Twenty-four entries: the named moves — Extract Function, Guard Clauses, Inline Variable, Reorder Parameters — applied by the tool, one command each. Before, after, the diff, and the sentences it printed about what it had done. Five of them are not edits: four are refusals, and one finds work without doing it.

Every file  Where a move reaches past the file it started in, every file is here — including the ones that did not have to change. Changing a signature and not its callers is not half a refactoring; it is a broken program. So the declaration and the calls appear together, in their own tabs, and you can watch the behaviour move from one to the other and stay the same.

Generated  Every after and every diff below is what the fr binary actually produced, captured by cargo test --test site_data. A hand-typed “after” is a claim about the tool rather than a demonstration of it, and it goes stale the first time the tool improves. That test fails when the page and the tool disagree.

Whose code  The names are Fowler's and Beck's, and each entry says which book and which edition. The code is not theirs: every sample here is written for this page, in Python, to exercise the move the catalogue describes. Their examples are copyrighted, and a translation of one into Python would be a derivative of it. Go and read them — the books are where the judgement lives, and no tool has any of that.

    What is not here

    Most of the catalogue. Both books are largely about moves that need to know what a type is — Replace Conditional with Polymorphism, Replace Primitive with Object, Encapsulate Record — and this tool resolves names, not types. It would have to guess, and a refactoring that guesses is a find-and-replace with better manners.

    The three entries that decline are the honest shape of that boundary, and each declines for a different reason. Fowler's own Guard Clauses example is an if/else nest assigning to a result, and turning the else into an early return means deciding what the function returns on the path that used to fall through — a judgement about the code. delete refuses anything still referenced, which is what makes fr unused's list worth acting on. And a reorder that would put a defaulted parameter before a required one is refused because Python will not run it — a rule the refactoring has to know, since tree-sitter parses the broken result without complaint.

    Two entries cite neither catalogue and say so. Renaming a CSS class across a stylesheet and the markup that names it is a problem the books predate; dropping unused imports is housekeeping nobody wrote a catalogue entry for. It seemed better to admit that than to attach a plausible-looking section number.

    The books

    • Refactoring: Improving the Design of Existing Code, 2nd ed. — Martin Fowler, 2018.
    • Refactoring, 1st ed. — Martin Fowler with Kent Beck, 1999, and the online catalogue that carries it forward.
    • Tidy First? — Kent Beck, 2023. Small, reversible, one at a time.
    • Test-Driven Development by Example — Kent Beck, 2002. Where the refactor step comes from.
    • Implementation Patterns — Kent Beck, 2007.
