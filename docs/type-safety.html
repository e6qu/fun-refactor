1. The program we will fix

A workshop builds bicycles. A bill of materials lists the parts, an invoice bills the customer, and the books still run on old British money: twelve pence to a shilling, twenty shillings to a pound. The file below carries no annotations at all. Python runs it. Node runs it. Both give wrong answers without a word of complaint.

Read it and find the five bugs:

  • invoice_line takes its four arguments in any order and never complains.
  • Money looks like every other number, and pence pass for pounds.
  • Whoever wrote advance typed darft for draft, so no invoice ever leaves drafts. The workshop hums, the bikes roll out, and no bill ever follows them.
  • Hand bill its ids backwards and it invoices the bicycle for one customer.
  • load_bom_line hands every field on as text, even the ones that are secretly numbers.

The program keeps all five secrets until someone runs it.

Point either checker at the file and it refuses outright. Not for the bugs, which it can't see: for the missing annotations. mypy --strict demands a type on every function, and tsc --strict rejects every implicit any. Annotations are the price of admission. Pay it, and each section below teaches the checker to catch one more of the five.

2. Simple types

Start with invoice_line. Type its arguments str, int and bool, and the checker turns the mixed-up call away. The annotations cost nothing at run time: Python never evaluates them, and TypeScript deletes them.

Money needs the same treatment. A price and a discount rate are both bare numbers, so nothing stops you handing them over the wrong way round. Split them: TypeScript erases the brand entirely, and Python charges about 20 ns for the constructor call.

Now the gift note, which may be missing. Reach for cast and you silence the checker; the crash waits for run time. Write the branch instead. The checker follows an if and drops None inside it, a move Typed Racket named occurrence typing. Call a function in between, though, and you lose the narrowing. The branch costs one comparison. The cast costs nothing and checks nothing, which is the whole trade.

3. Aliases and units

An alias renames a type without changing it, so it enforces nothing. When two same-shaped values must never trade places, reach for NewType in Python or a brand in TypeScript: a genuinely distinct type. TypeScript erases the brand outright; NewType leaves the value alone and charges about 20 ns per call. The parts file measures spokes by count and tubing by the meter, and those must never swap.

Watch the arithmetic, though. Add two branded numbers and the brand falls off. Give the quantities typed operations instead, and width times height comes out an area, a unit neither factor had. This safety has a price: every quantity becomes an object, about 135 ns to build in Python. Right for a bill of materials, wrong inside a numeric loop.

A status typed str accepts every typo, including the darft from section 1. Write the three real values into the type, and the checker turns the rest away. Both languages erase literal types, so this costs nothing.

4. Domain types

Only parse_email can turn a string into an EmailAddress. That's a domain type: it states a fact about your problem, and you can't hold one unless the fact is true. Scott Wlaschin calls the alternative primitive obsession. Keep the constructor in one module, because neither checker can stop a cast written somewhere else. The type is free. You pay for the check once, where you put it.

Swap two same-shaped ids and nothing notices. Give them two types, and the checker catches the swap, at no run-time cost.

Give escaped text its own class, not a subtype of str, and you close both doors: raw text can't reach the renderer, and nobody can escape the escaped text twice. The cost is one allocation per value.

Here the two languages part ways. TypeScript matches shapes everywhere; Python matches names. Declare a Protocol and Python matches shapes too: any class with the right method counts, including one you can't edit. A Protocol exists for the checker alone unless you mark it runtime-checkable.

5. States and stages

A distinct name keeps two values apart. It can't stop you building nonsense. For that, reshape the data until the nonsense has nowhere to live. Give each state its own type: a settled payment carries its receipt, and a pending one has no field to put one in. You pay one real tag field, plus a comparison to read it. Alexis King draws exactly this line, between labelling a value and modelling it. The second makes illegal states unrepresentable.

Stages work the same way. Let send return the only invoice record_payment accepts, and paying a draft becomes a type error instead of a guard you hope somebody wrote. Each transition allocates one object; the types themselves are free. Rust calls this typestate.

6. Parse, don't validate

The outside world hands your program text. Validate it, and you check the value and pass the same string on, so the next reader checks it again. Parse it, and you return a different type, which every later function demands. Alexis King named the rule and gave it its slogan: write functions on the data you wish you had. You pay for the parse once, at the border. After that the types carry the fact, and by run time they're gone.

One honest limit: your type records that the check ran, and the world keeps moving without you. Parse a port, and somebody can still take it before you bind it.

7. Fake types

Build a type that holds anything the input can hold, and you hand the checker nothing to refuse. The faithful Json type is the classic. It looks careful, and it spreads: it turns up in every signature that touches the data, and every field access needs a cast, an assertion nobody checks. Decoding isn't parsing, and nothing pushes you to convert: json.loads returns Any, and JSON.parse returns unknown.

Copying an external system's shape into your own types springs the same trap. Resources with a kind, a name and an attribute bag describe the config format perfectly and tell your program nothing: a server and a database share one type, every field is optional, and a misspelled key waits for whoever runs it. Model what your program needs, and read the foreign shape in one place.

Ask one question of every type you add: what does it refuse? If every value the source can produce fits, you've written documentation, and it cost you a checker.

8. Functions as values

A function's type is what it takes and what it returns. Leave it open, and the checker waves through a sort key it can't call. Write it down, and the mistake dies at the keyboard. The call is still a call.

Handler tables collect this dividend daily. Declare one handler shape, and the checker holds every entry to it: you catch the handler wired to the wrong case while you're still typing. At run time, the same lookup, the same call.

Wrap a function carelessly, and you lose its signature, and every argument check with it. Keep the signature, and the wrapper stays honest. Either way, the wrapper adds one call frame.

One everyday shape closes the section. Replace the hand-rolled loop with a chain that takes its test and its extractor as values, and the checker types every step. The two languages price it differently: Python's map and filter are lazy and build nothing, while each JavaScript filter and map allocates a fresh array.

9. Composition and monads

A monad is just a monoid in the category of endofunctors.

Anonymous

You already use three:

  • a comprehension that flattens a list of lists,
  • await, which unwraps an answer that arrives later,
  • the if that clears away a value that may be missing.

Those three share one shape, called a monad: a way in (Ok, Promise.resolve, a one-element list) and a chaining step that returns the same wrapper (and_then, flatMap, bind, then, await). map is the version for a step that can't fail. Here are the wrappers you'll meet:

  • Option: the answer may be missing. Neither language ships it; | None and optional chaining cover it.
  • Result: the step failed, and the reason matters.
  • List: many answers at once, chained with flatMap or a comprehension.
  • Promise: the answer arrives later, chained with await.
  • Writer: an audit line travels beside the value.
  • IO: a description of an effect, performed later at the edge.

Reach for your own language's tools first: None narrowing, exceptions at the edge, comprehensions, async and await. Hand-rolled monads aren't idiomatic in either language, and most teams treat them as friction. Only Result tends to earn its keep, so this page builds Result and stops there. Return None and every failure collapses into the same empty answer. Return a Result and each failure carries its reason, and and_then only runs the next step if the last one succeeded. Wlaschin calls this picture railway-oriented programming: two tracks and one switch. Every step allocates a wrapper, about 95 ns in Python.

Now the failure sits in the signature, where an exception never was. A caller can't forget it, and the checker refuses a quote spent as a number.

Purity is the one idea on this page the checker can't see at all. A function typed int to int can peek at the clock, and the checker never blinks. So move whatever it reaches for into its signature: hand remaining the time, and a test pins the answer down. An argument is the cheapest thing on this page.

Most pipelines carry nothing extra, and then you need none of this. Composition is the types lining up, and a step out of order is a type error on its own.

10. Exercises

Exercise 1: make the typo impossible

A typo killed one branch, and the checker can't see it. Turn the typo into a type error, and catch a forgotten status while you're there.

Hint

Section 3 for the literal type. Section 5 for an exhaustive match with assert_never, or a switch with a never default.

Exercise 2: name the units and the flags

Two call sites disagree about the argument order, and both pass. A row of bare booleans invites what Robert Harper calls boolean blindness. Give the units types and the flags names.

Hint

Section 3 for the units. For the flags, use a frozen dataclass or an object type with named fields.

Exercise 3: parse the user once

A user arrives as JSON, then travels as a loose dictionary, so every function re-checks it. Parse once at the edge, then delete the checks.

Hint

Section 6. Write one parse function that returns a User or raises, call it in summary, and let the field types travel.

Exercise 4: separate the currencies

Each amount keeps its currency in a string beside it, so the checker happily adds dollars to euros and calls it money. Move the currency into the types and that sum stops passing.

Hint

In Python, write one class per currency and a constrained type variable, [M: (Usd, Eur)]. In TypeScript, take a generic currency parameter and wrap the second argument in NoInfer, which pins the currency to the first amount.

Exercise 5: give each failure its reason

Three lookups can each fail, and all three collapse into one None. Rebuild the chain on Result.

Hint

Section 9. Write three small functions returning Result, and thread them with and_then.

Those figures come from one laptop, Python 3.14 and Node 26, and yours will differ. Remember the shape, not the numbers. Anything the checker alone uses is free, because it vanishes before the program runs. Compile the TypeScript above and the alias, the brand, the literal union, the interface and the satisfies leave no trace; only the enum, the class and the values survive. You pay for what exists: an object to allocate, a member to look up, a value to validate. Freezing a dataclass roughly triples the cost of building one, and a validating model costs a hundred times a plain dictionary. Both earn their keep at a border and rarely inside a loop.

Count the other costs too:

  • Data from the wild arrives dirty, and a model that holds only clean values can't load the record you need to repair.
  • A parser that stops at the first bad field can't collect every mistake at once.
  • Types named ValidThis and CheckedThat multiply.
  • Every invariant you add is a promise your fixtures must keep before they can build anything at all.

How does this page work?

Type in any cell, press a button, and a real tool runs in your tab. No server anywhere; the tab is the whole machine.

Run, Python. Pyodide is CPython compiled to WebAssembly. The first click loads it from a CDN. Each run hands your cell to the interpreter with fresh globals and shows what it printed.

Type check, Python. PyPI carries mypy as a pure-Python wheel, so Pyodide can install it in the browser. The button installs mypy==1.18.2, writes your cell to /cell.py on the virtual filesystem with a strict mypy.ini beside it, and calls mypy's API. The words are mypy's, character for character.

TypeScript. tsc was always JavaScript, so one CDN script is the whole compiler. Diagnostics use the same strict flags as the repository's tests; Run transpiles and evaluates.
