A tutorial

Type safety, from primitives to monads

A type is a claim the compiler checks on every build. This page walks that idea up, in eight steps: what a primitive type can say, what a domain type can say, where to parse, and how typed functions compose. Each step ends where the next one starts.

Every example appears twice, Python 3.14 on the left and TypeScript 5.9 on the right. Every example is a real file in this repository, and CI holds each one to the verdict printed on it: mypy --strict and tsc --strict accept the ones marked accepted and reject the ones marked rejected. Examples marked runs in CI also execute. Nothing on this page is a claim about a checker that a checker has not answered.

1. Simple types

str, int, float and bool are the types most code is written in. Each one makes a small claim: this value is text, this one is a number. The checker enforces that claim and nothing more.

The first example is a transfer between two accounts. Both account numbers are strings, so the call that swaps them is well typed. The checker keeps its promise; the promise is too small.

A simple type can also be the wrong claim. float says "any real number, approximately", and money is exact. Ten cents, three times, is thirty cents, and 0.1 + 0.1 + 0.1 is not 0.3 in either language. Integer cents carry the same prices without the approximation.

Both defects have the same shape: the type accepts values the program never means. The rest of this page is about narrowing that gap.

2. Aliases and units

A type alias gives a name to an existing type. The name documents intent at every signature that uses it, and that is all it does. The checker treats the alias and the original as the same type, so an alias stops no bug.

To make the checker enforce the name, the type has to be distinct. Python spells that NewType. TypeScript has no built-in spelling, and the common idiom is a brand: an intersection with a property that exists only in the type system. In both languages the new type costs nothing at run time.

The payoff is the rejected call. Seconds and meters are both numbers, and now they are not interchangeable. The 1999 Mars Climate Orbiter was lost to a pound-seconds value read as newton-seconds; the type system is the cheap place to catch that class of mistake.

Strings have the same problem in another costume. A status written as str accepts every string ever typed, including the misspelled ones. A literal type lists the values that exist.

3. Domain types

A domain type carries a fact about your problem, not about memory. An email address is not any string; it is a string a specific check accepted. The pattern has three parts: a distinct type, one function that constructs it, and no other way to get one. Code that holds an EmailAddress can rely on the check without repeating it.

The same pattern retires the very first bug on this page. Give each kind of account its own type, and the swapped call stops compiling.

Domain types can also describe states. A payment that is pending has no receipt. One class with an optional receipt field allows four combinations, and two of them are nonsense. Two types, one per state, allow the two that exist, and the checker makes every reader handle both.

4. Parse, don't validate

Domain types raise a question: where do they come from? The outside world hands a program strings. Command lines, environment variables, HTTP bodies and files all arrive untyped, and something has to check them.

Validating checks a value and passes it along unchanged. The knowledge that the check happened lives nowhere, so every reader checks again.

Parsing checks a value and returns a different type. The result proves the check ran, the checker carries that proof to every caller, and the inner checks come out. The rule, named by Alexis King: parse, don't validate. Do it once, at the edge of the system.

The network edge works the same way, and both ecosystems have a library for it: pydantic in Python, zod in TypeScript. Declare the shape once. The library checks the input, reports what is wrong, and returns a value whose type the checker knows.

After this section, a program has two zones. At the edge, raw input is parsed into domain types, and failures are handled where they can be reported. Inside, every function takes domain types, and the checker guarantees the garbage never gets that far.

5. Functions as values

A function has a type too: what it takes, and what it returns. Once that type is written down, functions can be passed around and checked like any other value.

A function that takes or returns a function is a higher-order function. The interesting ones are wrappers: retry, memoize, log. A wrapper is only safe when it keeps the wrapped signature, and both languages can state that. Python spells it with type parameters, [**P, R]. TypeScript spells it with a generic argument tuple.

6. Pure functions

A function is pure when the same arguments always produce the same result and nothing else happens: no clock, no network, no global state. Purity is not in the type signature, and the signature offers a strong hint. A function whose answer depends only on its parameters has to receive everything it needs.

The clock became a parameter, and the function became a table of facts a test can check. This pairs with section 4: parse at the edge, keep effects at the edge, and let the core be pure functions between domain types. The edge stays thin, and the core stays testable.

7. Composition and monads

Small pure functions become programs by composition: the output of one is the input of the next. Types make composition safe. A pipeline compiles only when the steps fit, so reordering or skipping a step is a compile error, not a production incident.

Real steps can fail. The plain spelling of failure is None or null in the return type, and each caller has to stop and check before continuing. It works, and it stacks up.

A Result keeps the pipeline shape with failure inside it. It holds either a value or a reason. and_then applies the next step to a value and passes a failure straight through, so the chain reads like the happy path and the first failure wins.

This shape has a name. A wrapper type with a way in (Ok), a way to transform (map), and a way to chain steps that return the wrapper (and_then, also called flatMap or bind) is a monad. You already use monads: Promise chains with then, and arrays chain with flatMap. The word names the pattern; the pattern is the part that matters.
