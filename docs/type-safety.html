A tutorial

Type safety, from primitives to monads

A type names the values a place in your program can hold: bool names two, a Status can name exactly three, and the checker reads your code and rejects every path that puts anything else there. This tutorial starts from one file of working, badly typed code. It types the swapped invoice arguments first, then the units and the ids, then parses the input once at the border, and it ends with functions that compose.

1. The program we will fix

One program runs through this whole page. A small workshop builds bicycles from parts: a bill of materials lists what goes into each model with quantities and costs, and an invoice bills the customer who buys one. The books are kept in old British money, where twelve pence (d) make a shilling (s) and twenty shillings make a pound, so £1 3s 6d is one pound, three shillings and sixpence. Here is the code, condensed to one file. The type checker, at its strictest, accepts every line of it.

Each function hides a bug that reached production. bom_line and invoice_line take every argument as Any, which is how one customer's invoice read 80 xTrue at handlebar gripd +tax. Money travels as bare numbers, so apply_discount cannot tell the total from the rate, and the swapped call goes through. advance compares bare strings, and the misspelled darft freezes every invoice in its draft stage. bill takes two look-alike ids as plain strings, so an invoice can be addressed to a bicycle. load_bom_line hands every field of the parts file on as text.

The tutorial removes these weaknesses in order: first the invoice line and the money, then the units and the statuses, then the ids, then the borders. Sections 6 through 8 compose the typed pieces into programs. Nothing of this file survives unchanged, and the closing section shows the finished version.

Some sections end with a short quiz: read the cell, call the verdict yourself, and then see what the checker actually said. When you get those right without looking, the section has done its job.

2. Simple types

Most code is written in str, int, float and bool. Each of these makes a small claim about a value: it is text, or it is a number. The checker holds that claim faithfully. The trouble is that the claim is usually much smaller than what your program means.

Start with the mangled invoice. Each line of an invoice shows a description, a price in pence, a quantity, and whether the line is taxed, and invoice_line formats one such line. As the seed file has it, with every argument Any, every call passes the scan, including the one with all four arguments in the wrong order; the customer who read 80 xTrue at handlebar gripd was the first to notice. Written with ordinary str, int and bool, the checker catches that same call while it reads the file. TypeScript rejects all four arguments. Python rejects three: True passes where an int belongs, because Python's bool is a subclass of int, a surprise worth meeting early. The mix of checked and unchecked code has a name and a lineage: gradual typing, worked out in the Lisp family for Typed Racket, where typed and untyped code share one program and Any is the seam.

Simple types run out of power quickly, though. The seed's bill addresses an invoice, and takes a customer id and a product id as two strings. Swap them at the call site and the checker stays quiet, because both are the same type, and the invoice goes out addressed to a bicycle. Programmers call this kind of code stringly typed. Hold the example in mind; its fix arrives in section 4.

Money shows the same weakness from another angle. In the seed, a price and a discount rate are both bare numbers, so when apply_discount gets its arguments in the wrong order, the checker has nothing to object to. Give the total and the rate their own types, and the swap stops getting through. Integer pence also happen to add exactly where floats drift, and you can watch that by pressing Run, but the checker never sees it. The typing lesson is the swap.

One more habit completes the basics. The gift note on an invoice line is str | None, and calling upper on a note that may be missing is rejected. cast makes the checker look away, and the crash comes back at run time. Write the branch instead: the checker follows an if, and inside it the None is gone. Typed Racket, in the Lisp family, pioneered this as occurrence typing; Python and TypeScript call it narrowing, and every match and typeof test on this page leans on it. The checker only trusts a narrowing it can watch hold still: narrow a shared attribute, call a function, and the narrowing is gone. Copy the value to a local first.

In each case the type is too broad, so wrong values fit. The rest of the page narrows the types until the wrong calls stop fitting.

3. Aliases and units

A type alias is a new name for an old type. The checker treats the two as identical, so an alias documents intent and enforces nothing. Enforcement needs a genuinely distinct type: NewType in Python, and in TypeScript a brand, an intersection with a marker that exists only in the type system.

In 1999 the Mars Climate Orbiter was lost because one team's software produced pound-force seconds and another's read newton-seconds. The type checker is the cheapest place to catch that class of mistake.

The seed's parts file keeps a unit column, and the workshop measures spokes by count, tubing by the meter, and grease by the kilogram. The bill of materials wants 1.8 meters of tubing for the frame and 36 spokes for each wheel, and cut_tubing expects a length, which a bare count fits perfectly. Both are plain numbers until NewType and a brand pull them apart.

Type theorists would say TypeScript's types are structural, anything with the right shape fits, and a brand makes one nominal, only the declared name fits. Either way, the distinct type is free at run time.

Aliases still earn their place when the point is naming. A long function type reads far better under a short name, and one edit updates every signature that uses it. A named constant does the same job for a magic number, a bare 30_000 whose meaning the reader is left to guess.

Here the shop's client retries failed requests. Every retry policy is a function from an attempt number and an error to a delay, and that shape used to be spelled out at three different signatures, with the default delay sitting in the code as a bare 30_000.

One limit is worth knowing about. A distinct type protects substitution, and arithmetic slips right past it: add two branded numbers and you get a plain number back, in both languages. If you multiply and add your quantities, give them typed operations instead: tubing lengths add to a length, weights add to a shipping weight, and the width of the chain-guard sheet times its height comes out an area, a third unit neither factor had. Then the units survive the arithmetic.

Strings share the weakness. A bare "paid" scattered through a codebase is a magic string, and a status typed str will accept anything, typos included; one production classic is a machine-learning option misspelled tahn for tanh, alive for months behind a str. A literal type writes down the values that exist, and the checker turns everything else away.

This is the seed's frozen invoice. The shop's invoices move through three stages: drafted, sent to the customer, and paid, and advance moves an invoice to its next stage. In the seed file, one branch compares against the misspelled string darft, so no invoice ever matches it, and the checker sees nothing wrong with comparing one string to another.

Literals belong in parameters too. A flag whose docstring says "text or binary" can say it in the type instead, where the checker can read it. The rejection cuts both ways: a variable typed as plain str can no longer be passed in, since it could hold anything at all.

The example is a log reader. Its mode parameter decides whether the file is read as text or as fixed-width binary records, and only those two words mean anything to it.

4. Domain types

A string becomes an EmailAddress only after parse_email has checked it. That is the whole idea of a domain type. Scott Wlaschin calls the habit of building everything out of raw strings and numbers primitive obsession, and the cure has three parts: a distinct type, one function that constructs it, and no other way to get one. Functional programmers call that function a smart constructor. Neither checker can fully enforce the third part, because NewType and a brand cast work anywhere, so keep the constructor in one module and treat a stray cast as a review failure. Code that receives an EmailAddress can then skip the check, and the checker turns away anyone who passes a plain string instead. The same door can hold any business rule: a quantity that must stay between 1 and 99 is one bounds check in one constructor. Save the treatment for values where a mix-up is easy to make and expensive to ship; wrapping everything buys ceremony.

The workshop sends each invoice by email, and later a reminder. The address arrives from a web form, typed by a person, so it needs a check, and the question is where that check lives.

The same recipe retires the seed's billing bug, held over from section 2. Give customers and products their own id types, and the swapped call no longer passes the check.

Alexis King, whose parsing rule the next section borrows, draws a line worth keeping in view: a distinct name keeps two values apart, and only reshaping the data makes a bad value impossible to build. The ids above are names. The states below are reshaped data.

Domain types can also describe states. A pending payment has no receipt yet. Model both states as one class with an optional receipt, and you allow four combinations, two of which cannot exist. Model each state as its own type, and only the real two remain. This is a tagged union, which TypeScript calls a discriminated union. The goal is what Yaron Minsky called making illegal states unrepresentable. With an assert_never arm or a never default in place, the checker demands that every reader handle every state: exhaustiveness checking. The throw inside that arm is deliberate: when nothing uses the narrowed value, a forgotten case can slip through as never, and the runtime error is the net under the net.

The shop's payments show the pattern. A payment starts out pending, and once it settles, it has a receipt id. There is no such thing as a settled payment without a receipt, and no pending payment has one.

One kind of mistake is still standing. The statuses have safe names, and the payment cannot hold an impossible mixture, but nothing stops code from paying an invoice that was never sent; the seed's advance would take the call and fail at run time. Give each stage its own type, and let send return the only type record_payment accepts. Rust programmers call this typestate. In Python and TypeScript it is plain classes and return types, and a step out of order fails the scan.

The wrapper deserves one more turn of the screw. A NewType is a subtype, so an HtmlText built on str would still fit back into escape_html, and a second escape would sail through. Make the wrapper its own class, and both directions close: raw text cannot reach the renderer, and escaped text cannot be escaped again. React ships this discipline; its renderer refuses plain strings as HTML.

One asymmetry between the languages earns the section's last example. TypeScript checks shapes everywhere: any object with the right members fits. Python's classes match by name, and typing.Protocol, added in 3.8, is the opt-in: declare the methods a carrier must have, and any class that has them counts, including one from a library you cannot edit. No inheritance, and the checker still holds every carrier to the signature.

5. Parse, don't validate

Where do domain types come from? The outside world only ever hands your program text. A command line is a list of strings. An environment variable is a string. An HTTP body is a string of JSON. A file is bytes. None of it arrives with a type, and something has to turn it into the objects the rest of the program works with.

Validation checks a value and hands it on as the same plain string, so later code cannot tell the check ever ran, and checks again. Security researchers call that scattered checking shotgun parsing, and it is exactly where malformed input slips through. Parsing runs the same check and returns a different type, so functions that receive the typed value never repeat it. Alexis King gave the rule its name, parse, don't validate, and its best slogan: write functions on the data you wish you had. Parse once, at the edge.

The seed's load_bom_line splits a row of the parts file and hands every field on as text, so qty and cost get converted wherever someone remembers to. The command line is the same problem at its smallest. The workshop's server starts from a terminal with a line like serve port=8080 verbose=true, and argv gives the program nothing but strings. In the before version the settings travel as a dictionary of strings, and every function that wants the port converts and re-checks it for itself. In the after version parse_argv reads the strings once and returns a Config whose port is an int. A bad command line fails right there, with a message, before the program does any work.

The order that arrives over HTTP is the same story. json.loads or JSON.parse gives you a shapeless value, one parse function turns it into an Order or raises with the reason, and every function after that takes the Order. The exercise at the end of the page walks exactly this case. Libraries exist that write the parse function from a declared schema; they check at run time, so on this page they appear only in the closing table, as the contrast.

Parse input at the boundary, and pass Config, Order and the other domain values around instead of raw strings. Hand a function the raw dictionary anyway, and the checker refuses it; that refusal is the new row under each example above. One honest limit: a type records that a check happened, and the world can change afterwards. A parsed port can be taken by the time you bind it. The type spared you the re-checking; the operating system still gets a vote.

6. Functions as values

Functions have types too: what they take, and what they return. Write that type down, and a function can be passed around and checked like any other value. Leave it open, with Callable[..., int] or any, and the checker will wave through key functions that crash the moment they run.

The shop again: a page lists orders, cheapest first. Sorting needs a key, and a key is a function passed as a value.

A function that takes or returns another function is a higher-order function. The most useful ones are wrappers: retry, memoize, log. A wrapper is only safe if it preserves the signature it wraps, and both languages can express that. Python uses type parameters, [**P, R]; TypeScript uses a generic argument tuple.

The wrapper here is retry. Fetching from a flaky upstream service fails now and then, so the shop wraps fetch to try three times before giving up. The question the types answer: after wrapping, does the checker still know what fetch takes and returns?

Each language also has a higher-order idiom you will meet every day. In Python it is the decorator: @timed above a definition means "pass this function through timed and bind the result to the same name". In JavaScript it is the array chain: map, filter and reduce each take a typed callback, and the types flow all the way down the chain. Python has map and filter as well, though a comprehension usually reads better. JavaScript has decorators as well, on classes and their members, though not on plain functions.

7. Pure functions

A function is pure when the same arguments always give the same result and nothing else happens: no clock, no network, no globals. The formal name is referential transparency, and any call to such a function could be replaced by its value. Be clear about what the checker sees here: nothing. A function typed int to int is free to read the clock, and the scan stays quiet. Purity is a discipline, and what the checker can hold is the shape it leaves behind: a function that depends only on its parameters has to receive everything it needs.

remaining shows the trade. Read the clock inside, and a test can never pin the answer down. Take now as a parameter, and the answer becomes a fact a test can state, and the dependency gets a type: hand remaining a bare number instead of a datetime, and the checker refuses the call.

Handing dependencies in like this is dependency injection at its smallest. Gary Bernhardt calls the resulting shape functional core, imperative shell: effects at the boundary, pure functions between domain types in the middle. The next section shows what the checker can hold once even the effects become values.

8. Composition and monads

You build programs by connecting small functions: one function's output is the next one's input. The types make the connection safe. Put the steps in the wrong order, and the checker rejects the call.

Quoting an order takes two steps: convert the raw order, then price it. The RawOrder was already parsed in section 5; here it changes hands. The check that matters is that each function accepts exactly what the previous one returns, and the rejection below shows the wrong handoff refused.

Real steps fail. Returning None or null works, but every kind of failure collapses into the same empty answer. With a Result, each step returns either a value or a reason, and and_then runs the next step only when it got a value. The code follows the success case, and when a step fails, the later steps never run. Wlaschin teaches this as railway-oriented programming: two tracks, and one switch.

Here is what the checker holds. A Result[int] will not pass where an int is expected, so a caller cannot forget the failure case the way they can forget an exception. An exception never shows up in a signature; a Result does, and the rejection above shows a quote spent as a number being refused.

This pattern is called a monad: Ok puts a value into the wrapper, and and_then (also called flatMap or bind) chains steps that return the same wrapper. The monad laws just say the plumbing behaves: grouping chained calls differently does not change the result, and Ok on its own changes nothing. map is the version of and_then for a step that cannot fail. Here are the familiar wrappers and what each one handles:

  • Option handles absence. Neither language ships the wrapper; x | None narrowing in Python and optional chaining in TypeScript cover the same ground natively.
  • Result handles failure with a reason. You met it above.
  • List handles many answers at once. A comprehension and flatMap are its chaining step.
  • Promise handles answers that arrive later. then chains and flattens.
  • Writer carries a log beside the value, so the audit trail arrives with the answer.
  • IO describes an effect without performing it, so policies like retry become ordinary functions over descriptions.

Before you rewrite a codebase around any of this, a warning. Reach for the language's own tools first: None narrowing, exceptions at the edge, comprehensions, async and await. Hand-rolled monads are not idiomatic in Python or TypeScript, and most teams will experience them as friction. The Writer and IO below are small models to learn the pattern from. What carries over is the idea: keep values and failures flowing through steps whose types the checker can see, even when you spell it with the language's own tools.

Here is a Writer, hand-rolled for a price calculation the workshop wants to audit. Each step returns its result together with its log line, and the chain concatenates the trails, so the audit arrives with the answer as plain data. The checker's part: a Logged total will not pass where a bare number is expected, so nobody drops the log by accident.

The IO below wraps the flaky fetch from section 6. Store the call in a value instead of performing it, and retry wraps that stored value once; the loop disappears from the network functions. Nothing runs until the edge of the program calls run, and the checker keeps the stages apart: an IO[str] is not a str, so code cannot spend the description as if it were already the answer.

As for the definition you may have heard, "a monad is just a monoid in the category of endofunctors": that is a true sentence from category theory, and a long-running joke about explanations that explain nothing. Keep the working definition: a way in, a chain, and map for the steps that cannot fail.

9. Exercises

These five exercises reuse the mistakes from the seed file, each in a new place. You get working, badly typed code, and your job is to rewrite it so the checker catches the defect described. One solution sits behind a toggle in each block, along with the diff, and every solution goes through the same CI checks as the rest of the page.

Exercise 1: make the typo impossible

A typo has killed one branch of this status function, and the checker has no way to see it. Make the typo a type error the scan catches, and a forgotten status too.

Hint

Section 3: a literal type. Section 4: an exhaustive match with assert_never, or a switch with a never default.

Exercise 2: name the units and the flags

Two call sites disagree about the argument order, and both pass the check. A row of bare booleans invites what Robert Harper calls boolean blindness: the call reads true, false, true and tells you nothing. Give the units real types and the flags names. A type cannot tell which bare number you meant, so label every value where it enters; after that, two labelled quantities can no longer change places quietly, and the solution's misuse row shows the swap rejected.

Hint

Section 3 for the units. For the flags, a frozen dataclass or an object type with named fields.

Exercise 3: parse the user once

A user arrives as JSON and then travels as a loose dictionary, so every function re-checks whichever fields it touches. Parse once at the edge, then delete the checks.

Hint

Section 5. Write one parse function that returns a User or raises, call it in summary, and let the field types travel.

Exercise 4: separate the currencies

An amount is a number with its currency in a string beside it, and the mismatch is caught at run time, if at all. Move it into the types, so adding dollars to euros no longer passes the check. In the TypeScript solution, NoInfer, which arrived in TypeScript 5.4, pins the currency to the first amount, so the second cannot widen it to a union of both.

Hint

In Python, one class per currency and a constrained type variable, [M: (Usd, Eur)]. In TypeScript, a generic currency parameter and NoInfer on the second argument.

Exercise 5: give each failure its reason

Three lookups can each fail, and all three failures collapse into one None. Rebuild the chain on Result, so each failure keeps its reason.

Hint

Section 8. Three small functions returning Result, and and_then to thread them.

10. The toolbox, compared

The page has now used most of what the two languages offer for building types. They differ in two ways that matter: what the checker holds at the scan, and what still exists once the program runs. Most of these constructs vanish at run time. In Python, only an enum, a class and a validating model leave something behind; in TypeScript, only an enum, a class and a schema survive erasure, and only the model and the schema ever check a value. The runtime end of the axis is its own tradition: Racket's contracts and Clojure's spec live there, and pydantic and zod are that idea in these two languages. The last column says when each construct arrived; everything on this page runs on Python 3.12 and TypeScript 5.4 or newer. Strict has fine print in both: the Python checker skips the bodies of unannotated functions unless told otherwise, and TypeScript leaves array indexing optimistic unless noUncheckedIndexedAccess is on. This page checks with it on.

The bill deserves open eyes too. Data from the wild is dirty, and a model that can only hold clean values cannot even load the record you need to repair. A parser that stops at the first bad field cannot collect every mistake a user made at once. Types named ValidThis and CheckedThat multiply until nobody knows which one a function wants. And every invariant in a constructor is a promise your test fixtures must satisfy before they can build anything at all.

A rule of thumb runs through the page. Start with the closed set when the values have a fixed menu. Add the label when two same-shaped values must never swap. Give the data a shape when the fields have names, and reshape it when some combinations are impossible. Keep validation at the border, in one constructor or one schema, and let every type after it stand for a check that already happened.
