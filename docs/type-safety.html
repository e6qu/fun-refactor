1. The program we will fix

A workshop builds bicycles. A bill of materials lists the parts, an invoice bills the customer, and the books use old British money: twelve pence to a shilling, twenty shillings to a pound. Both checkers accept every line of this file at their strictest settings.

Read it for the five bugs neither checker can see. Every argument is typed Any, the type that accepts any value and switches the checker off. Money looks like every other number. A status is misspelled darft. Two ids swap without complaint. And the parts file hands on every field as text.

2. Simple types

Because Any accepts everything, invoice_line takes its four arguments in any order you like. Type them str, int and bool, and the checker turns the mixed-up call away. Annotations cost nothing when the program runs: Python never evaluates them, and TypeScript deletes them.

Money needs the same treatment. A price and a discount rate are both bare numbers, so nothing stops you handing them over the wrong way round. Splitting them is nearly free: TypeScript erases the brand, and Python charges about 20 ns for the constructor call.

Now the gift note, which may be missing. Reach for cast and you silence the checker, and the crash comes back at run time. Write the branch instead: the checker follows an if and drops None inside it. Typed Racket named this occurrence typing. Call a function in between, though, and you lose the narrowing again. The branch costs one comparison, and the cast costs nothing and checks nothing, which is the whole trade.

3. Aliases and units

An alias renames a type without changing it, so it enforces nothing. Reach for NewType in Python or a brand in TypeScript when you want a genuinely distinct type. A brand is erased outright, and a NewType leaves the value alone and charges about 20 ns for the call. The parts file measures spokes by count and tubing by the meter, and those must never trade places.

Aliases still earn their keep as names. Give the callback shape one, and give the magic number a constant. Neither exists once the program starts.

Watch the arithmetic, though: add two branded numbers and the brand falls off. Give the quantities typed operations instead, and width times height comes out an area, a unit neither factor had. This one has a price: every quantity becomes an object, about 135 ns to build in Python. Right for a bill of materials, wrong inside a numeric loop.

A status typed str accepts every typo, including the darft from section 1. Write the three real values into the type and the checker turns the rest away, at no run-time cost, since literal types are erased in both languages.

Do the same to a parameter: a mode that means text or binary, and nothing else.

4. Domain types

A string becomes an EmailAddress only after parse_email accepts it. That is a domain type: it states a fact about your problem, and you cannot get one without the fact being true. Scott Wlaschin calls the alternative primitive obsession. Keep the constructor in one module, because neither checker can stop a cast written somewhere else. The type is free; you pay only for the check, once, where you put it.

Two ids of the same shape swap silently until you give them two types, which costs nothing at all at run time.

Give escaped text its own class rather than a subtype of str, and you close both doors: raw text cannot reach the renderer, and escaped text cannot be escaped twice. A class per value is the one cost here, an allocation apiece.

The two languages differ here. TypeScript matches shapes everywhere, Python matches by name. Declare a Protocol and Python matches shapes too, so any class with the right method counts, including one you cannot edit. A Protocol exists for the checker alone unless you mark it runtime-checkable.

5. States and stages

A distinct name keeps two values apart. It does not stop you building nonsense in the first place. To do that, reshape the data until the nonsense has nowhere to live. Give each state its own type: a settled payment carries its receipt, and a pending one has no field to put one in, at the cost of one real tag field and one comparison to read it. Alexis King draws exactly this line, between labelling a value and modelling it, and the second is what makes illegal states unrepresentable.

Stages work the same way. Let send return the only invoice that record_payment accepts, and paying a draft becomes a type error rather than a guard you hope somebody wrote. Every transition allocates a new object, and the types themselves are free. Rust calls this typestate.

6. Parse, don't validate

The outside world hands your program text. Validate it and you check the value, then pass the same string on, so the next reader checks it again. Parse it and you check the value, then return a different type, which every later function demands. Alexis King named the rule and gave it its slogan: write functions on the data you wish you had. You pay for the parse once, at the border, and nothing after it, because the types are gone by then.

One honest limit. Your type records that the check ran, and the world moves on without you. Parse a port and somebody can still take it before you bind it.

7. Fake types

Build a type that holds anything the input can hold and you give the checker nothing to refuse. A faithful Json type is the classic. It looks careful, and it spreads: it turns up in every signature that touches the data, and every field access needs a cast, which is an assertion nobody checks and which costs nothing precisely because it does nothing. Decoding is not parsing, and nothing pushes you to convert, because json.loads returns Any and JSON.parse returns unknown.

You walk into the same trap when you copy an external system's shape into your own types. Resources with a kind, a name and an attribute bag describe the config format perfectly and tell your program nothing: a server and a database share one type, no field is required, and a misspelled key waits for whoever runs it. Model what your program needs, and read the foreign shape in one place.

So ask one question of every type you add: what does it refuse? If every value the source can produce fits, you have written documentation that costs you a checker and gives you nothing back.

8. Functions as values

A function's type is what it takes and what it returns. Leave it open and the checker waves through a sort key it cannot call. Writing the type down costs nothing; the call is still a call.

Handler tables are where this pays off daily. Declare one handler shape, and the checker holds every entry to it, so you catch the handler wired to the wrong case while you are still typing it. At run time it is the same lookup and the same call as the untyped version.

Wrap a function carelessly and you lose its signature, and every argument check with it. Keep the signature and the wrapper stays honest. Either way the wrapper adds one call frame.

One everyday shape closes the section. Replace a hand-rolled loop with a chain that takes its test and its extractor as values, and the checker types every step of it. The shape differs in cost between the languages: Python's map and filter are lazy and build nothing, while each JavaScript filter and map allocates a new array.

9. Composition and monads

A monad is just a monoid in the category of endofunctors.

Anonymous

You already use three: a comprehension that flattens a list of lists, await that unwraps an answer arriving later, and the check that clears away a value which may be missing.

Those three share one shape, called a monad: a way in (Ok, Promise.resolve, a one-element list) and a chaining step that returns the same wrapper (and_then, flatMap, bind, then, await). map is the version for a step that cannot fail. Here are the wrappers you will meet:

  • Option: the answer may be missing. Neither language ships it; | None and optional chaining cover it.
  • Result: the step failed, and the reason matters.
  • List: many answers at once, chained with flatMap or a comprehension.
  • Promise: the answer arrives later, chained with await.
  • Writer: an audit line travels beside the value.
  • IO: the effect is described now and performed later.

Reach for your own language's tools first: None narrowing, exceptions at the edge, comprehensions, async and await. Hand-rolled monads are not idiomatic in either language, and most teams meet them as friction. Only Result usually earns its keep. Return None and every failure collapses into the same empty answer; return a Result and each one carries its reason, while and_then runs the next step only after a value. Wlaschin calls the picture railway-oriented programming: two tracks and one switch. Every step allocates a wrapper, about 95 ns in Python.

Now the failure sits in the signature, where an exception never was. A caller cannot forget it, and the checker refuses a quote spent as a number.

A Writer does the same job for an audit trail. Every step that touches an amount leaves its line, and the checker stops you dropping the trail on the way out, for a wrapper and a log concatenation per step.

Purity is the one idea on this page the checker cannot see at all. A function typed int to int is free to read the clock, and nothing complains. What you can do is move whatever it reaches for into its signature: hand remaining the time, and a test can pin the answer down. An argument is the cheapest thing on this page.

An IO applies that move to effects. Store the call instead of performing it and the effect becomes a value the checker can see: retry wraps the description once instead of living inside every network function, and nothing happens until the edge of the program calls run. Each action is a closure, about 33 ns in Python.

Most pipelines carry nothing extra, and then you need none of this. Composition is just the types lining up, and a step out of order is a type error on its own.

The epigraph, by the way, is a true sentence from category theory and a long-running joke about explanations that explain nothing.

10. Exercises

Exercise 1: make the typo impossible

A typo has killed one branch, and the checker cannot see it. Turn the typo into a type error, and catch a forgotten status while you are there.

Hint

Section 3 for the literal type. Section 5 for an exhaustive match with assert_never, or a switch with a never default.

Exercise 2: name the units and the flags

Two call sites disagree about the argument order, and both pass. A row of bare booleans invites what Robert Harper calls boolean blindness. Give the units types and the flags names.

Hint

Section 3 for the units. For the flags, use a frozen dataclass or an object type with named fields.

Exercise 3: parse the user once

A user arrives as JSON and then travels as a loose dictionary, so every function re-checks it. Parse once at the edge, then delete the checks.

Hint

Section 6. Write one parse function that returns a User or raises, call it in summary, and let the field types travel.

Exercise 4: separate the currencies

An amount is a number with its currency in a string beside it. Move the currency into the types, so adding dollars to euros stops passing.

Hint

In Python, write one class per currency and a constrained type variable, [M: (Usd, Eur)]. In TypeScript, take a generic currency parameter and wrap the second argument in NoInfer, which pins the currency to the first amount.

Exercise 5: give each failure its reason

Three lookups can each fail, and all three collapse into one None. Rebuild the chain on Result.

Hint

Section 9. Write three small functions returning Result, and thread them with and_then.

Those figures come from one laptop, Python 3.14 and Node 26, and yours will differ. The shape is what to remember. Anything the checker alone uses is free, because it is not there when the program runs: compile the TypeScript above and the alias, the brand, the literal union, the interface and the satisfies leave no trace in the output, while only the enum, the class and the values survive. What costs is what exists, whether that is an object to allocate, a member to look up or a value to validate. Freezing a dataclass roughly triples the cost of building one, and a validating model costs a hundred times a plain dictionary. Both are worth it at a border and rarely worth it inside a loop.

Count the other costs too. Data from the wild is dirty, and a model that holds only clean values cannot load the record you need to repair. A parser that stops at the first bad field cannot collect every mistake at once. Types named ValidThis and CheckedThat multiply. And every invariant you add is a promise your fixtures must satisfy before they can build anything at all.

How does this page work?

Every cell is editable, and the buttons run real tools in the tab. There is no server.

Run, Python. Pyodide is CPython compiled to WebAssembly. The first click loads it from a CDN; each run hands your cell to the interpreter with fresh globals and shows what it printed.

Type check, Python. PyPI carries mypy as a pure-Python wheel, so Pyodide can install it in the browser. The button installs mypy==1.18.2, writes your cell to /cell.py on the virtual filesystem with a strict mypy.ini beside it, and calls mypy's API. The words are mypy's, character for character.

TypeScript. tsc was always JavaScript, so one CDN script is the whole compiler. Diagnostics use the same strict flags as the repository's tests; Run transpiles and evaluates.

Lint. Ruff is Rust, compiled to WebAssembly. It is Ruff itself.

To edit this page. The prose is docs/type-safety.html.
