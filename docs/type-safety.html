A tutorial

Type safety, from primitives to monads

A type says what a value means, not only how it is stored. This tutorial starts from one file of working, badly typed code. It types the swapped invoice arguments first, then the units and the ids, then parses the input once at the border, and it ends with functions that compose.

1. The program we will fix

One program runs through this whole page. A small workshop builds bicycles from parts: a bill of materials lists what goes into each model with quantities and costs, and an invoice bills the customer who buys one. The books are kept in old British money, where twelve pence (d) make a shilling (s) and twenty shillings make a pound, so £1 3s 6d is one pound, three shillings and sixpence. Here is the code, condensed to one file. The type checker, at its strictest, accepts every line of it.

Each function hides a bug that reached production. bom_line and invoice_line take every argument as Any, which is how one customer's invoice read 80 xTrue at handlebar gripd +tax. product_cost and invoice_total keep pounds in floats, and the totals drift pennies from the ledger. advance compares bare strings, and the misspelled darft freezes every invoice in its draft stage. bill takes two look-alike ids as plain strings, so an invoice can be addressed to a bicycle. load_bom_line hands every field of the parts file on as text.

The tutorial removes these weaknesses in order: first the invoice line and the money, then the units and the statuses, then the ids, then the borders. Sections 6 through 8 compose the typed pieces into programs. Nothing of this file survives unchanged, and the closing section shows the finished version.

How to read the examples

Each example is a block with a Before, the code with a weakness, and an After, the same code with the types doing more work. The Diff button between them swaps the panes to the exact change. Some blocks end with a row labelled Now a type error: a call the Before version accepted, and the After version turns into a rejection. A toggle under that row shows the checkers' verbatim messages. Some sections end with a short quiz: read the code, call the verdict yourself, and then see what the checker actually said. When you get those right without looking, the section has done its job.

2. Simple types

Most code is written in str, int, float and bool. Each of these makes a small claim about a value: it is text, or it is a number. The checker holds that claim faithfully. The trouble is that the claim is usually much smaller than what your program means.

Start with the mangled invoice. Each line of an invoice shows a description, a price in pence, a quantity, and whether the line is taxed, and invoice_line formats one such line. As the seed file has it, with every argument Any, every call passes the scan, including the one with all four arguments in the wrong order; the customer who read 80 xTrue at handlebar gripd was the first to notice. Written with ordinary str, int and bool, the checker catches that same call while it reads the file. TypeScript rejects all four arguments. Python rejects three: True passes where an int belongs, because Python's bool is a subclass of int, a surprise worth meeting early.

Simple types run out of power quickly, though. The seed's bill addresses an invoice, and takes a customer id and a product id as two strings. Swap them at the call site and the checker stays quiet, because both are the same type, and the invoice goes out addressed to a bicycle. Programmers call this kind of code stringly typed. Hold the example in mind; its fix arrives in section 4.

Sometimes the simple type is the wrong claim outright. The seed's invoice_total sums pounds as floats, and it matters that three parts at two shillings, a tenth of a pound each, come to exactly six shillings. float stores approximate reals, and money needs to be exact. Everything passes the scan, and the totals drift a penny away from the ledger. Integer pence fix it: Python's int is exact at any size, JavaScript's number is exact for whole numbers up to 2⁵³, and carrying by twelves and twenties turns out to be formatting, not arithmetic.

All three problems have the same shape: the type accepts values the program never intends. Everything that follows is about closing that gap.

3. Aliases and units

A type alias is a new name for an old type. The checker treats the two as identical, so an alias documents intent and enforces nothing. Enforcement needs a genuinely distinct type: NewType in Python, and in TypeScript a brand, an intersection with a marker that exists only in the type system.

In 1999 the Mars Climate Orbiter was lost because one team's software produced pound-force seconds and another's read newton-seconds. The type checker is the cheapest place to catch that class of mistake.

The seed's parts file keeps a unit column, and the workshop measures spokes by count, tubing by the meter, and grease by the kilogram. The bill of materials wants 1.8 meters of tubing for the frame and 36 spokes for each wheel, and cut_tubing expects a length, which a bare count fits perfectly. Both are plain numbers until NewType and a brand pull them apart.

Type theorists would say TypeScript's types are structural, anything with the right shape fits, and a brand makes one nominal, only the declared name fits. Either way, the distinct type is free at run time.

Aliases still earn their place when the point is naming. A long function type reads far better under a short name, and one edit updates every signature that uses it. A named constant does the same job for a magic number, a bare 30_000 whose meaning the reader is left to guess.

Here the shop's client retries failed requests. Every retry policy is a function from an attempt number and an error to a delay, and that shape used to be spelled out at three different signatures, with the default delay sitting in the code as a bare 30_000.

One limit is worth knowing about. A distinct type protects substitution, and arithmetic slips right past it: add two branded numbers and you get a plain number back, in both languages. If you multiply and add your quantities, give them typed operations instead: tubing lengths add to a length, weights add to a shipping weight, and the width of the chain-guard sheet times its height comes out an area, a third unit neither factor had. Then the units survive the arithmetic.

Strings share the weakness. A bare "paid" scattered through a codebase is a magic string, and a status typed str will accept anything, typos included. A literal type writes down the values that exist, and the checker turns everything else away.

This is the seed's frozen invoice. The shop's invoices move through three stages: drafted, sent to the customer, and paid, and advance moves an invoice to its next stage. In the seed file, one branch compares against the misspelled string darft, so no invoice ever matches it, and the checker sees nothing wrong with comparing one string to another.

Literals belong in parameters too. A flag whose docstring says "text or binary" can say it in the type instead, where the checker can read it. The rejection cuts both ways: a variable typed as plain str can no longer be passed in, since it could hold anything at all.

The example is a log reader. Its mode parameter decides whether the file is read as text or as fixed-width binary records, and only those two words mean anything to it.

4. Domain types

A raw string is not an email address. A domain type states that fact: an EmailAddress is a string one particular check accepted. Building everything from raw strings and numbers has a name, primitive obsession, coined by Scott Wlaschin. The recipe against it has three parts: a distinct type, one function that constructs it, and no other way to obtain one. Functional programmers call that function a smart constructor. Neither checker can fully enforce the last clause, since NewType and a brand cast can be invoked anywhere. Keep the constructor in one module, and treat a stray cast as a review failure. Any code holding an EmailAddress can then rely on the check without repeating it.

The workshop sends each invoice by email, and later a reminder. The address arrives from a web form, typed by a person, so it needs a check, and the question is where that check lives.

The same recipe retires the seed's billing bug, held over from section 2. Give customers and products their own id types, and the swapped call no longer passes the check.

Domain types can also describe states. A pending payment has no receipt yet. Model both states as one class with an optional receipt, and you allow four combinations, two of which cannot exist. Model each state as its own type, and only the real two remain. This is a tagged union, which TypeScript calls a discriminated union. The goal is what Yaron Minsky called making illegal states unrepresentable. With an assert_never arm or a never default in place, the checker demands that every reader handle every state: exhaustiveness checking.

The shop's payments show the pattern. A payment starts out pending, and once it settles, it has a receipt id. There is no such thing as a settled payment without a receipt, and no pending payment has one.

5. Parse, don't validate

Where do domain types come from? The outside world only ever hands your program text. A command line is a list of strings. An environment variable is a string. An HTTP body is a string of JSON. A file is bytes. None of it arrives with a type, and something has to turn it into the objects the rest of the program works with.

Validation checks a value and passes it along unchanged. Nothing records that the check happened, so every downstream reader checks again. Security researchers call that scattered version shotgun parsing, and it is exactly where malformed input slips through. Parsing runs the same check and returns a different type, so the result proves the check happened, and the type checker carries the proof to every caller. Alexis King gave the rule its name, parse, don't validate, and its best slogan: write functions on the data you wish you had. Parse once, at the edge.

The seed's load_bom_line is this problem in one line: it splits a row of the parts file and hands every field on as text, so the conversion of qty and cost happens wherever someone remembers to do it. Take the command line first, because it is the same problem at its smallest. The workshop's server is started from a terminal, as servers are, with a line like serve port=8080 verbose=true. argv is nothing but strings; the operator typed port=8080, and "8080" stays text until something converts it. In the before version the settings travel as a dict of strings, so every function that wants the port converts and re-checks it for itself. In the after version, parse_argv reads the strings once and returns a Config whose port field is an int, and the type guarantees it. A bad command line fails immediately, with a message, before the program does any work.

The network edge is the same story. When a customer places an order, the shop's API receives an HTTP request whose body is one long JSON string. json.loads or JSON.parse gives you a shapeless dictionary, and the shape still needs checking. This is what pydantic and zod are for: libraries that check the shape at run time and hand the static checker a typed result. You declare the shape once, as a schema; the library either hands you a real Order with typed fields, or an error naming the field and the reason. The Python handler below goes from raw body to Order in a single call; the TypeScript one parses the JSON first and hands the shapeless value to the schema. Neither touches the dictionary afterwards.

From here on, your program has two zones. At the edge, raw text becomes domain types, and failures get reported where someone can act on them. Inside, every function receives domain types, and the checker keeps raw text out: a string can no longer wander past the edge unparsed.

6. Functions as values

Functions have types too: what they take, and what they return. Write that type down, and a function can be passed around and checked like any other value. Leave it open, with Callable[..., int] or any, and the checker will wave through key functions that crash the moment they run.

The shop again: a page lists orders, cheapest first. Sorting needs a key, and a key is a function passed as a value.

A function that takes or returns another function is a higher-order function. The most useful ones are wrappers: retry, memoize, log. A wrapper is only safe if it preserves the signature it wraps, and both languages can express that. Python uses type parameters, [**P, R]; TypeScript uses a generic argument tuple.

The wrapper here is retry. Fetching from a flaky upstream service fails now and then, so the shop wraps fetch to try three times before giving up. The question the types answer: after wrapping, does the checker still know what fetch takes and returns?

Each language also has a higher-order idiom you will meet every day. In Python it is the decorator: @timed above a definition means "pass this function through timed and bind the result to the same name". In JavaScript it is the array chain: map, filter and reduce each take a typed callback, and the types flow all the way down the chain. Python has map and filter as well, though a comprehension usually reads better. JavaScript has decorators as well, on classes and their members, though not on plain functions.

7. Pure functions

A function is pure when the same arguments always give the same result and nothing else happens: no clock, no network, no globals. Pass now into remaining, below, and a test chooses the time instead of racing the system clock. The formal name is referential transparency: any call could be replaced by its value. A signature cannot prove purity, since a function typed int to int can still read the clock. The discipline still leaves a mark: a function that depends only on its parameters has to receive everything it needs, so the clock shows up as an argument.

The example is a countdown. remaining reports how long is left until a deadline, which sounds too small to get wrong, until a test tries to pin its answer down and the answer moves.

Once the clock is a parameter, the function is a table of facts, and a test can pin any entry. Handing dependencies in like this is dependency injection at its smallest. It also completes the picture from section 5: parse at the edge, keep the effects at the edge, and let the core be pure functions between domain types. Gary Bernhardt calls the shape functional core, imperative shell.

8. Composition and monads

Small pure functions turn into programs by composition: one function's output is the next one's input. Types are what make that safe. The pipeline passes the check only if the steps fit together, so a step out of order is a type error, caught long before it can become a production incident.

Quoting an order is a pipeline: convert the raw order, then price it. The RawOrder arrives from the section 5 edge, already shaped; what this section adds is the handoff. Each step has its own input and output type, and that is the whole safety story.

Real steps fail. The plain way to say so is to return None or null, and it works; the cost is that every caller stops to check, and every kind of failure collapses into the same empty answer. A Result keeps the failure inside the pipeline: each step returns either a value or a reason, and and_then feeds values forward while passing any failure straight through. The chain reads like the happy path, and the first failure wins. Wlaschin teaches this as railway-oriented programming: two tracks, and one switch.

Result gives each step two outcomes, a value or a reason, and and_then runs the next step only after a value. That shape has a name: a wrapper with a way in (Ok) and a chaining step that returns the wrapper (and_then, also called flatMap or bind) is a monad. The fine print, called the monad laws: chaining is associative, and Ok is its neutral step. A map that only transforms the contents comes free: chain a step that cannot fail. The standard monads answer the standard problems:

  • Option handles absence. Neither language ships the wrapper; x | None narrowing in Python and optional chaining in TypeScript cover the same ground natively.
  • Result handles failure with a reason. You met it above.
  • List handles many answers at once. A comprehension and flatMap are its chaining step.
  • Promise handles answers that arrive later. then chains and flattens.
  • Writer carries a log beside the value, so the audit trail arrives with the answer.
  • IO describes an effect without performing it, so policies like retry become ordinary functions over descriptions.

Before you rewrite a codebase around any of this, a warning. Reach for the language's own tools first: None narrowing, exceptions at the edge, comprehensions, async and await. Hand-rolled monads are not idiomatic in Python or TypeScript, and most teams will experience them as friction. The Writer and IO below are compact models to learn the shape from, not a recommendation. The shape is what transfers: it tells you what a clean pipeline looks like even when you spell it natively.

Here is a Writer, hand-rolled. Each step returns its result together with its log line, and the chain concatenates the trails. The log arrives with the answer, as ordinary data you can assert on, attach to a response, or throw away.

The scene for the Writer is a price calculation the shop wants to audit: every step that touches the amount should leave a line saying what it did.

And here is an IO. Store the network call in a value instead of performing it. retry then wraps that stored call once, instead of living as a loop pasted into every network function. Nothing runs until the edge of the program calls run.

The scene for the IO is the flaky upstream service from section 6, fetched with a retry, except this time the retry policy and the business logic never share a function body.

As for the definition you may have heard, "a monad is just a monoid in the category of endofunctors": that is a true sentence from category theory, and a long-running joke about explanations that explain nothing. Keep the working definition. A way in, a flattening chain, and a map for free.

9. Exercises

By this point every weakness in the seed file has a fix on this page. These five exercises hand you its cousins: working, badly typed code, each carrying one of the same defects in a new place. Your job is to rewrite each one so the checker catches the defect described. One solution sits behind a toggle in each block, along with the diff, and every solution goes through the same CI checks as the rest of the page.

Exercise 1: make the typo impossible

A typo has killed one branch of this status function, and the checker has no way to see it. Make the typo a type error the scan catches, and a forgotten status too.

Hint

Section 3: a literal type. Section 4: an exhaustive match with assert_never, or a switch with a never default.

Exercise 2: name the units and the flags

Two call sites disagree about the argument order, and both pass the check. A row of bare booleans invites what Robert Harper calls boolean blindness: the call reads true, false, true and tells you nothing. Give the units real types and the flags names. A type cannot tell which bare number you meant, so label every value where it enters; after that, two labelled quantities can no longer change places quietly, and the solution's misuse row shows the swap rejected.

Hint

Section 3 for the units. For the flags, a frozen dataclass or an object type with named fields.

Exercise 3: parse the user once

A user arrives as JSON and then travels as a loose dictionary, so every function re-checks whichever fields it touches. Parse once at the edge, then delete the checks.

Hint

Section 5. Declare the shape with pydantic or zod, parse in summary, and let the field types travel.

Exercise 4: separate the currencies

An amount is a number with its currency in a string beside it, and the mismatch is caught at run time, if at all. Move it into the types, so adding dollars to euros no longer passes the check.

Hint

In Python, one class per currency and a constrained type variable, [M: (Usd, Eur)]. In TypeScript, a generic currency parameter and NoInfer on the second argument.

Exercise 5: give each failure its reason

Three lookups can each fail, and all three failures collapse into one None. Rebuild the chain on Result, so each failure keeps its reason.

Hint

Section 8. Three small functions returning Result, and and_then to thread them.
