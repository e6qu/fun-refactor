A tutorial

Change code so its types catch more mistakes

Start with the five mistakes below, then compare the proposed changes and their checks. Each new concept appears with its example. These are code-change lessons; a passing type checker does not replace behavior tests or a Lean proof of a stated property.

1. The program we will fix

The example is a bicycle invoicing program. It stores product IDs, customer IDs, prices, quantities and invoice states. Its untyped functions accept values in the wrong slots, so a call can run while producing the wrong invoice.

Every code cell is editable. In the first cell, print bill("roadster", "Mrs. Pemberton") and press Run. The swapped customer and product arguments produce an invoice addressed to the product. The following sections add types and checks that distinguish those roles.

That's one of five mistakes waiting in the file:

  • Unchecked argument types let mismatched values reach invoice_line.
  • Prices are plain numbers, and some functions count in pence while others count in pounds.
  • advance compares the status against darft, so no invoice leaves the draft state and no customer gets billed.
  • Customer and product IDs share an unmarked type, so a checker cannot distinguish the swapped call to bill.
  • load_bom_line passes every field on as text, quantities and prices included.

Press Type check on the starting program. Python's ty accepts its unannotated functions, while TypeScript's tsc --strict reports implicit any parameters. Neither result identifies all five application mistakes. Gradual typing allows unchecked parts alongside checked code; follow each change to see which mistake it catches.

2. Simple types

Start with invoice_line. A parameter is a named slot for an argument. This function needs text for a description, integers for price and quantity, and a boolean tax flag. Distinguishing those types catches some swapped arguments.

Annotate the parameters with str, int and bool. Put a price in the description slot and ask the checker again. It reports the mismatched types. Price and quantity are both integers, so swapping those two still needs distinct units or a behavior test. Annotations do not add automatic runtime validation.

A price and a discount rate can both be numbers while meaning different things. In the next example, reversing the arguments to apply_discount produces the wrong amount. The function needs types that distinguish these roles.

Define distinct Pence and Rate types, then try the reversed call. The type checker reports a mismatch. TypeScript removes these type labels from generated JavaScript. Python's NewType constructor still runs and returns the supplied value; this page does not measure its cost.

A gift note can be text or missing: str | None describes those two possibilities. A cast tells the checker to trust you without checking the value. Casting a missing note to text therefore cannot prevent a runtime failure.

Check note is None and return before calling the text method. On the remaining path, the checker can treat the note as text. This is narrowing: a condition reduces the possible types at that point. The condition also executes when the program runs.

3. Aliases and units

The parts file measures spokes by count and tubing by length. An alias gives an existing type another name; it does not create a distinct unit. A Meters alias for a number therefore still accepts a spoke count.

Use Python's NewType or a TypeScript brand to distinguish units during checking. A brand is a type label added to an otherwise ordinary value. Pass a spoke count to cut_tubing and inspect the type error. Runtime input checks must still establish that outside values have the promised units.

Watch the arithmetic, though. Add two branded lengths and the sum comes back a plain number, brand gone.

Define operations for the units: adding two lengths returns a length, while multiplying them returns an area. The example uses objects to hold those values, so construction and arithmetic allocate objects. Measure the actual workload before judging that runtime cost.

A plain string allows the misspelling darft wherever draft was intended. The next change restricts an invoice status to the three supported values.

List the supported statuses in the type, then try darft and press Type check. The checker rejects it. Literal types restrict checked code; input arriving as text still needs runtime validation.

4. Domain types

A customer email field can contain an empty string, surrounding spaces or text without @. Checking it once but returning an ordinary string loses the distinction between checked and unchecked text.

Return EmailAddress from parse_email and require it in send_receipt. This is a domain type: a type representing a rule of the application. Keep construction with the check, because a cast can otherwise claim the rule without enforcing it. The validation still runs; the label alone does not validate an address.

A customer ID and a product ID can both be strings. Giving them distinct types lets the checker distinguish the argument slots that were swapped in the first section.

Give each ID a distinct type and repeat the reversed call. The checker reports the mismatch. Outside strings still need the appropriate conversion, and casts can bypass the distinction.

Escaping replaces characters so text can be inserted into an HTML context. Returning an ordinary string loses the record of that operation, allowing callers to escape it twice.

Return HtmlText from the escaper and require it in this renderer. The checked signatures distinguish raw text from the example's escaped text. The wrapper allocates a value. This does not establish safety for every HTML, URL or script context.

The shipping code needs a carrier with a quote_pence method. Another package can provide that method without inheriting our carrier class. The next example describes the required methods so the checker can recognize that object.

Declare a Protocol and Python matches shapes too: the outside class counts as it stands, with no inheritance asked for. A Protocol exists for the checker alone unless you mark it runtime-checkable.

5. States and stages

A payment with a boolean settled flag and an optional receipt allows a contradictory combination: settled with no receipt. Describe pending and settled payments as different shapes so checked construction must supply the right fields.

Give Settled a required receipt field and Pending no receipt. Try constructing a settled payment without its receipt and inspect the error. These are tagged states: the program distinguishes which shape it holds before reading its fields.

An invoice should be sent before it can be paid. A comment leaves every caller responsible for remembering that order. Distinct stage types can make the permitted order part of the function signatures.

Let send return SentInvoice and require that type in record_payment. Try passing a draft and inspect the type error. This pattern is called typestate: the available operations depend on the represented stage. The example's transitions also create runtime objects.

6. At the border

Command-line arguments arrive as text. If each function receives a dictionary of strings, it must check again whether the port is numeric and within range. The dictionary's type does not record that a prior check succeeded.

Validate the port in parse_argv and return Config. Functions that accept this checked shape can use its numeric port. Keep untrusted construction at that boundary, the point where outside input enters the application.

The type records the validation performed on the input. It cannot reserve a network port or ensure another process will leave it available. Opening the connection still needs its own error handling.

A general JSON value can be a number, text, a list, an object or null. Passing that broad shape through every function forces each reader to check its fields again. Convert it into the application's required fields before doing invoice arithmetic.

Validate each decoded line and return Line. Downstream code can then read line.pence without asserting its type through a cast. JSON decoding only reads the data format. Neither json.loads nor JSON.parse establishes the application's required fields and types.

An external configuration can describe servers and databases with one generic bag of attributes. That shape permits misspelled keys and missing fields. Define the distinct settings your own program requires, and validate the external data when importing it.

Model the fields this application uses and reject invalid input during conversion. Ask what a proposed type rules out. A broad shape that accepts the same invalid combinations leaves the original behavior checks necessary.

7. Functions as values

The picking list takes a function that chooses a sorting key. This is a callback: a function supplied for another function to call. Its declared argument and result types should describe invoice lines and the keys the sort expects.

Declare what the callback accepts and returns. Pass a callback requiring a different input and ask the checker to identify the mismatch. The declared type adds a check before execution; the program still performs the same callback call.

Take the handler table next, one handler per order status.

A handler table maps each supported status to a function. Declare the argument and result types those functions must share. Try an incompatible handler and inspect the reported mismatch. Runtime dispatch remains a lookup followed by a call.

A retry helper receives a function and returns a wrapped function. Giving both the broadest possible type loses the original argument checks. The next change preserves the wrapped function's signature.

Preserve the argument and return types through the wrapper, then try a call with an invalid argument. The checker should still report it. The wrapper itself executes and adds a function call each time it is used.

8. Composition and monads

The next examples chain operations that can have several answers, no answer or a delayed answer:

  • a comprehension that flattens a list of lists,
  • await, which unwraps an answer that arrives later,
  • the if that clears away a value that may be missing.

A common design puts a value inside a container and provides a way to chain the next operation. A monad is that design with rules for consistent chaining. The examples illustrate the idea; they do not prove those rules. Introduce each container by the problem it handles:

  • Option: the answer may be missing. Neither language ships it; | None and optional chaining cover it.
  • Result: the step failed, and the reason matters.
  • Promise: the answer arrives later; chain it with await.

Use the language's ordinary operations when they fit: missing-value checks, exceptions, comprehensions and await. Here, quote has three distinct failures: invalid quantity, insufficient stock and missing price. Returning None for all three loses the reason.

Return Ok with the price or Err with a failure reason. The example's and_then calls the next step only after success and carries a failure forward unchanged. This makes the result and failure cases visible to the caller. Each step can allocate a wrapper; no runtime benchmark is recorded here.

A function is pure when its result depends on its arguments and it has no outside effects. Its ordinary type signature alone does not establish that property. Reading the clock inside remaining makes the result depend on when it runs.

Pass the current time as now. A test can then choose a fixed time and check a thirty-minute result. Inspect the implementation too: accepting the argument alone cannot establish that the function has no other effects.

9. Exercises

Exercise 1: make the typo impossible

The misspelled status prevents one branch of advance from running. Restrict the status type and require a case for every supported status.

Hint

Section 3 for the literal type. Section 5 for an exhaustive match with assert_never, or a switch with a never default.

Exercise 2: name the units and the flags

Two call sites disagree about the argument order, and both run. A row of bare booleans at a call site tells the reader nothing. Give the units types and the flags names.

Hint

Section 3 for the units. For the flags, use a frozen dataclass or an object type with named fields.

Exercise 3: parse the user once

The user record arrives as JSON and travels on as a loose dictionary, so every function re-checks the fields before using them. Write one parse at the edge, then delete the checks downstream.

Hint

Section 6. Write one parse function that returns a User or raises, call it in summary, and let the field types travel.

Exercise 4: separate the currencies

A plain numeric amount does not distinguish dollars from euros. Give the currencies distinct types and check that adding them produces a type error.

Hint

In Python, write one class per currency and a constrained type variable, [M: (Usd, Eur)]. In TypeScript, take a generic currency parameter and wrap the second argument in NoInfer, which pins the currency to the first amount.

Exercise 5: give each failure its reason

Three lookups can each fail, and all three collapse into one None. Rebuild the chain on Result.

Hint

Section 8. Write three small functions returning Result, and thread them with and_then.

These tables describe runtime operations, not measured overhead. This page has no retained benchmark supporting nanosecond costs or cross-language speed comparisons. TypeScript removes type-only declarations from generated JavaScript. Python type objects, constructors, validation and data allocation can still do runtime work. Measure the same operation, inputs, versions and build settings against an explicit baseline before claiming a speed difference. The measurement guide explains that comparison.

Count the other costs too:

  • Data from the wild arrives dirty, and a model that holds only clean values can't load the record you need to repair.
  • A parser that stops at the first bad field can't collect every mistake at once.
  • Types named ValidThis and CheckedThat multiply.
  • Every invariant you add is a promise your fixtures must keep before they can build anything at all.
