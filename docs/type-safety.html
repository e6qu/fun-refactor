1. The program we will fix

A workshop builds bicycles. A bill of materials lists the parts, an invoice bills the customer, and the books are kept in old British money, where twelve pence make a shilling and twenty shillings a pound. Every line below passes the strictest scan.

Five bugs hide in it, and the checker cannot see one of them: Any arguments, money that looks like every other number, a status misspelled darft, two ids that swap freely, and a parts file that stays text.

2. Simple types

Any accepts the four arguments in any order. Real types do not.

A price and a discount rate are both bare numbers, so the swapped call goes through.

The gift note may be missing. cast silences the checker; a branch it can follow does not. Typed Racket named this occurrence typing, and narrowing does not survive a call that could change the value.

3. Aliases and units

An alias is another name for the same type, so it enforces nothing. NewType and a TypeScript brand make a genuinely distinct one, free at run time. The parts file measures spokes by count and tubing by the meter.

Aliases still earn their keep as names: one for a callback shape, one constant for a magic number.

Addition strips a brand, so give the quantities typed operations. Width times height comes out an area, a unit neither factor had.

A status typed str accepts every typo, including the seed's darft. A literal type writes down the three values that exist.

The same closure works on a parameter: a mode that means text or binary, and nothing else.

4. Domain types

A string becomes an EmailAddress only after parse_email accepts it. Scott Wlaschin calls the alternative primitive obsession. Keep the constructor in one module: neither checker can stop a cast made elsewhere.

Two ids of the same shape swap silently until they are two types.

A name keeps values apart. Reshaping the data makes the bad value impossible to build: a settled payment carries its receipt, a pending one cannot.

Stages work the same way. send returns the only invoice record_payment accepts, so paying a draft fails the scan. Rust calls this typestate.

Escaped text deserves its own class rather than a subtype, so raw text cannot reach the renderer and escaped text cannot be escaped twice.

TypeScript matches shapes everywhere. Python matches by name, and typing.Protocol is the opt-in: any class with the right method counts, including one you cannot edit.

5. Parse, don't validate

The outside world hands your program text. Validation checks it and passes the same string on, so the next reader checks again. Parsing runs the same check and returns a different type, and every function after it demands that type. Alexis King named the rule and its slogan: write functions on the data you wish you had.

One honest limit: the type records that a check happened, and the world can change afterwards. A parsed port can be taken by the time you bind it.

6. Fake types

A type that can hold anything the input can hold gives the checker nothing to refuse. The classic is a faithful Json type. It looks careful, and it is viral: it appears in every signature that touches the data, every use needs a cast to get at a field, and the casts are unchecked assertions. Decoding is not parsing, and the standard library will not stop you, because json.loads and JSON.parse hand back Any and unknown.

The same trap opens whenever you copy an external system's shape into your own types. A config format built from resources, names and attribute bags is exactly right for the format and useless to your program: nothing distinguishes a server from a database, no field is required, and a misspelled key is found by whoever runs it. Model what your program needs, and read the foreign shape in one place.

The test for a type worth having: can it refuse anything? If every value the source produces fits, the type is documentation with a checker's costs and none of its help.

7. Functions as values

A function's type is what it takes and returns. Leave it open and the checker waves through a key the sort cannot call.

The table of handlers is where this pays every day. Declare one handler shape, and the checker holds every entry to it, so a handler wired to the wrong case is caught while you write it.

A wrapper that loses the signature loses every argument check with it.

The everyday shape: a hand-rolled loop becomes a chain that takes its test and its extractor as values, and the checker types every step of it.

8. Pure functions

Same arguments, same result, nothing else. The checker sees none of this: a function typed int to int can still read the clock. What it can hold is the shape the discipline leaves behind, where the clock arrives as an argument with a type of its own.

9. Composition and monads

A monad is just a monoid in the category of endofunctors.

Anonymous

You already use three: a comprehension flattening a list of lists, await unwrapping an answer that arrives later, and the check that clears away a value which may be missing.

Those three share one shape, called a monad: a way in (Ok, Promise.resolve, a one-element list) and a chaining step that returns the same wrapper (and_then, flatMap, bind, then, await). map is the version for a step that cannot fail. The wrappers you meet:

  • Option: the answer may be missing. Neither language ships it; | None and optional chaining cover it.
  • Result: the step failed, and the reason matters.
  • List: many answers at once, chained with flatMap or a comprehension.
  • Promise: the answer arrives later, chained with await.
  • Writer: an audit line travels beside the value.
  • IO: the effect is described now and performed later.

Only one is usually worth writing yourself. Returning None collapses every failure into the same empty answer, while a Result carries the reason, and and_then runs the next step only after a value. The chain reads straight down, and the first failure ends it. Wlaschin calls the picture railway-oriented programming: two tracks and one switch.

The failure now sits in the signature, where an exception never was, so a caller cannot forget it and the checker refuses a quote spent as a number.

None of this is needed when the steps carry nothing extra. Then composition is just the types lining up, and a step out of order is a type error on its own.

The last two are worth reading and rarely worth writing. Reach for the language's own tools first, because hand-rolled monads are not idiomatic in either language and most teams meet them as friction. A Writer keeps the audit trail attached to the answer it explains, which is what you want when every step that touches an amount has to justify itself.

An IO stores the call instead of performing it, so a retry policy wraps the description once instead of living as a loop inside every network function, and nothing happens until the edge of the program calls run.

The epigraph, by the way, is a true sentence from category theory, and a long-running joke about explanations that explain nothing.

10. Exercises

Exercise 1: make the typo impossible

A typo has killed one branch, and the checker cannot see it. Make the typo a type error, and a forgotten status too.

Hint

Section 3: a literal type. Section 4: an exhaustive match with assert_never, or a switch with a never default.

Exercise 2: name the units and the flags

Two call sites disagree about the argument order, and both pass. A row of bare booleans invites what Robert Harper calls boolean blindness. Give the units types and the flags names.

Hint

Section 3 for the units. For the flags, a frozen dataclass or an object type with named fields.

Exercise 3: parse the user once

A user arrives as JSON and travels as a loose dictionary, so every function re-checks it. Parse once at the edge, then delete the checks.

Hint

Section 5. Write one parse function that returns a User or raises, call it in summary, and let the field types travel.

Exercise 4: separate the currencies

An amount is a number with its currency in a string beside it. Move it into the types, so adding dollars to euros no longer passes.

Hint

In Python, one class per currency and a constrained type variable, [M: (Usd, Eur)]. In TypeScript, a generic currency parameter and NoInfer on the second argument, which pins the currency to the first amount.

Exercise 5: give each failure its reason

Three lookups can each fail, and all three collapse into one None. Rebuild the chain on Result.

Hint

Section 9. Three small functions returning Result, and and_then to thread them.

11. The concepts

Every idea the page used, with the name people call it by, and when it does its work. Most of this is scan only: a type alias leaves nothing behind, and a brand leaves the plain value. An enum and a class are real objects that outlive the scan. pydantic and zod sit at the far end, checking values as they arrive and handing the checker a type in return.

12. The toolbox, compared

Two axes matter: what the checker holds at the scan, and what survives into the running program. Most of these vanish; only a validating model or schema ever checks a value, in the tradition of Racket's contracts and Clojure's spec. Everything here needs Python 3.12 or TypeScript 5.4, and strict has fine print in both: Python skips unannotated function bodies, and TypeScript leaves array indexing optimistic without noUncheckedIndexedAccess, which this page turns on.

The bill: data from the wild is dirty, and a model that holds only clean values cannot load the record you need to repair. A parser that stops at the first bad field cannot collect every mistake at once. Types named ValidThis and CheckedThat multiply. And every invariant is a promise your fixtures must satisfy before they can build anything.
