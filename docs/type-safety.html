A tutorial

Type safety, from primitives to monads

A type is a claim that the compiler checks on every build. This tutorial starts with the smallest claims and works up: richer types, parsing at the edges of the system, and functions that compose. Eight steps, and each one ends where the next begins.

Each example comes as a before and an after, in Python 3.14 and TypeScript 5.9 side by side, with a Diff button that shows the whole change. The examples are real files in this repository, and CI runs mypy --strict and tsc --strict over every one of them. All the errors you will see are static: the checker finds them by reading the source, before anything runs. Nothing on this page claims more than the checkers confirmed.

1. Simple types

Most code is written in str, int, float and bool. Each of these makes a small claim about a value: it is text, or it is a number. The checker holds that claim faithfully. The trouble is that the claim is usually much smaller than what your program means.

Here is the plainest possible case. order_line formats a line from a name, a price, a quantity and a gift flag. With Any, every call compiles, even the one that passes all four arguments in the wrong order; you find out at run time. With ordinary str, float, int and bool, the checker catches that same call while it reads the file.

Simple types run out of power quickly, though. transfer takes two account numbers, both strings, so the checker happily accepts the call that swaps them. Programmers call this kind of code stringly typed. Hold that example in mind; its fix arrives in section 3.

Sometimes the simple type is the wrong claim outright. float stores approximate reals, and money needs to be exact. Everything typechecks, and the totals quietly drift.

All three problems have the same shape: the type accepts values the program never intends. Everything that follows is about closing that gap.

2. Aliases and units

A type alias is a new name for an old type. The checker treats them as identical, so an alias documents your intent and enforces nothing. If you want enforcement, the type has to be genuinely distinct. Python has NewType for this. TypeScript gets there with a brand: an intersection with a marker property that exists only in the type system. Type theorists would say TypeScript's types are structural, where anything with the right shape fits, and a brand makes one nominal, where only the declared name fits. Either way, the distinct type is free at run time.

In 1999 the Mars Climate Orbiter burned up because one team's software produced pound-seconds and another's read newton-seconds. The type checker is the cheapest place to catch that class of mistake.

Aliases still earn their place when the point is naming. A long function type reads far better under a short name, and one edit updates every signature that uses it. A named constant does the same job for a magic number, a bare 30_000 whose meaning the reader is left to guess.

One limit is worth knowing about. A distinct type protects substitution, and arithmetic slips right past it: add two branded numbers and you get a plain number back, in both languages. If you multiply and add your quantities, give them a small class with typed operations. Then the units survive the arithmetic.

Strings share the weakness. A bare "paid" scattered through a codebase is a magic string, and a status typed str will accept anything, typos included. A literal type writes down the values that exist, and the checker turns everything else away.

Literals belong in parameters too. A flag whose docstring says "text or binary" can say it in the type instead, where the checker can read it. The rejection cuts both ways: a variable typed as plain str can no longer be passed in, since it could hold anything at all.

3. Domain types

There is a name for building everything out of raw strings and numbers: Scott Wlaschin calls it primitive obsession. The cure is a domain type, one that states a fact about your problem. An EmailAddress is a string that a particular check accepted. The recipe has three parts: a distinct type, one function that constructs it, and no other way to obtain one. Functional programmers call that function a smart constructor. Any code holding an EmailAddress can rely on the check without repeating it.

The same recipe retires the transfer bug from section 1. Give each kind of account its own type, and the swapped call no longer compiles.

Domain types can also describe states. A pending payment has no receipt yet. Model both states as one class with an optional receipt, and you allow four combinations, two of which cannot exist. Model each state as its own type, and only the real two remain. This is a tagged union, which TypeScript calls a discriminated union. The goal is what Yaron Minsky called making illegal states unrepresentable, and the checker demanding that every reader handle every state is exhaustiveness checking.

4. Parse, don't validate

Where do domain types come from? The outside world only ever hands your program text. A command line is a list of strings. An environment variable is a string. An HTTP body is a string of JSON. A file is bytes. None of it arrives with a type, and something has to turn it into the objects the rest of the program works with.

Validation checks a value and passes it along unchanged. The knowledge that the check happened is stored nowhere, so every downstream reader checks again; security researchers call the scattered version shotgun parsing, and it is exactly where malformed input slips through. Parsing checks the value and returns a different type. Same check, except now the result proves it happened, and the type checker carries that proof to every caller. Alexis King gave the rule its name, parse, don't validate, and its best slogan: write functions on the data you wish you had. Parse once, at the edge.

Take the command line first. argv is nothing but strings; the user typed port=8080, and "8080" stays text until something converts it. In the before version the settings travel as a dict of strings, so every function that wants the port converts and re-checks it for itself. In the after version, parse_argv reads the strings once and returns a Config whose port field is an int, and the type guarantees it. A bad command line fails immediately, with a message, before the program does any work.

The network edge is the same story. The response body is one long JSON string. json.loads or JSON.parse gives you a shapeless dictionary, and the shape still needs checking. This is what pydantic and zod are for. You declare the shape once, as a schema; the library either hands you a real Order with typed fields, or an error naming the field and the reason. The handler below goes from raw body to Order in a single line and never touches the dictionary.

From here on, your program has two zones. At the edge, raw text becomes domain types, and failures get reported where someone can act on them. Inside, every function receives domain types, and the checker guarantees that garbage never makes it that far.

5. Functions as values

Functions have types too: what they take, and what they return. Write that type down, and a function can be passed around and checked like any other value. Leave it open, with Callable[..., int] or any, and the checker will wave through key functions that crash the moment they run.

A function that takes or returns another function is a higher-order function. The most useful ones are wrappers: retry, memoize, log. A wrapper is only safe if it preserves the signature it wraps, and both languages can express that. Python uses type parameters, [**P, R]; TypeScript uses a generic argument tuple.

Each language also has a higher-order idiom you will meet every day. In Python it is the decorator: @timed above a definition means "pass this function through timed and bind the result to the same name". In JavaScript it is the array chain: map, filter and reduce each take a typed callback, and the types flow all the way down the chain. Python has map and filter as well, though a comprehension usually reads better. JavaScript has decorators as well, though only on class members.

6. Pure functions

A function is pure when the same arguments always give the same result and nothing else happens: no clock, no network, no globals. The formal term is referential transparency: any call could be replaced by its value. You can often read purity straight off the signature, because a function that depends only on its parameters has to receive everything it needs.

Once the clock is a parameter, the function is a table of facts, and a test can pin any entry. Handing dependencies in like this is dependency injection at its smallest. It also completes the picture from section 4: parse at the edge, keep the effects at the edge, and let the core be pure functions between domain types. Gary Bernhardt calls the shape functional core, imperative shell.

7. Composition and monads

Small pure functions turn into programs by composition: one function's output is the next one's input. Types are what make that safe. The pipeline compiles only if the steps fit together, so a step out of order is a compile error, caught long before it can become a production incident.

Real steps fail. The plain way to say so is to return None or null, and it works; the cost is that every caller stops to check, and every kind of failure collapses into the same empty answer. A Result keeps the failure inside the pipeline: each step returns either a value or a reason, and and_then feeds values forward while passing any failure straight through. The chain reads like the happy path, and the first failure wins. Wlaschin teaches this as railway-oriented programming: two tracks, and one switch.

This shape has a name. Any wrapper with a way in (Ok), a way to transform the contents (map), and a way to chain steps that themselves return the wrapper (and_then, also called flatMap or bind) is a monad. The standard ones map onto the standard problems:

  • Option handles absence. x | None narrowing in Python and optional chaining in TypeScript play this role.
  • Result handles failure with a reason. You met it above.
  • List handles many answers at once. A comprehension and flatMap are its chaining step.
  • Promise handles answers that arrive later. then chains and flattens.
  • Writer carries a log beside the value, so the audit trail arrives with the answer.
  • IO describes an effect without performing it, so policies like retry become ordinary functions over descriptions.

Two of them you have been using all along:

Here is a Writer, hand-rolled. Each step returns its result together with its log line, and the chain concatenates the trails. The log arrives with the answer, as ordinary data you can assert on, attach to a response, or throw away.

And here is an IO. Wrap the computation instead of running it, and effects become values you can hand around. A retry policy stops being a loop pasted into every network function; it becomes one combinator that wraps any description. Nothing actually runs until the edge of the program calls run.

Before you rewrite a codebase around any of this, a warning. Hand-rolled monads are not idiomatic in Python or TypeScript, and most teams will experience them as friction. These languages already ship the specialised forms: None narrowing, exceptions at the edge, comprehensions, async/await. Reach for those first. The shape is still worth carrying in your head, because those idioms are the monads, one per problem, and the shape tells you what a clean pipeline looks like even when you spell it natively.

As for the definition you may have heard, "a monad is just a monoid in the category of endofunctors": that is a true sentence from category theory, and a long-running joke about explanations that explain nothing. Keep the working definition. A way in, a map, and a flattening chain.

8. Exercises

Every exercise starts from working, badly typed code. Your job is to rewrite it so the checker catches the defect described. One solution sits behind a toggle in each block, along with the diff, and every solution goes through the same CI checks as the rest of the page.

Exercise 1: make the typo impossible

A typo has killed one branch of this status function, and the checker has no way to see it. Make the typo a compile error, and a forgotten status too.

Hint

Section 2: a literal type. Section 3: an exhaustive match with assert_never, or a switch with a never default.

Exercise 2: name the units and the flags

Two call sites disagree about the argument order, and both compile. A row of bare booleans invites what Robert Harper calls boolean blindness: the call reads true, false, true and tells you nothing. Give the units real types and the flags names, so only one of the calls survives.

Hint

Section 2 for the units. For the flags, a frozen dataclass or an object type with named fields.

Exercise 3: parse the user once

A user arrives as JSON and then travels as a loose dictionary, so every function re-checks whichever fields it touches. Parse once at the edge, then delete the checks.

Hint

Section 4. Declare the shape with pydantic or zod, parse in summary, and let the field types travel.

Exercise 4: separate the currencies

An amount is a number with its currency in a string beside it, and the mismatch is caught at run time, if at all. Move it into the types, so adding dollars to euros no longer compiles.

Hint

In Python, one class per currency and a constrained type variable, [M: (Usd, Eur)]. In TypeScript, a generic currency parameter and NoInfer on the second argument.

Exercise 5: give each failure its reason

Three lookups can each fail, and all three failures collapse into one None. Rebuild the chain on Result, so each failure keeps its reason.

Hint

Section 7. Three small functions returning Result, and and_then to thread them.
