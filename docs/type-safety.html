A tutorial

Type safety, from primitives to monads

A type is a claim the compiler checks on every build. This page walks that idea up in eight steps: what a primitive type can say, what a domain type can say, where to parse, and how typed functions compose. Each step ends where the next one starts.

Every example shows a before and an after, each in Python 3.14 and TypeScript 5.9 side by side. The Diff button shows the whole change between them. Every example is a real file in this repository, and CI checks each one with mypy --strict and tsc --strict. Every error on this page is a static one: the checker finds it by scanning the source, before the program runs. The page only claims what the checkers confirmed.

1. Simple types

str, int, float and bool are the types most code is written in. Each one makes a small claim: this value is text, this one is a number. The checker enforces that claim faithfully, and the claim is often smaller than what the program means.

Start with the plainest case. A function formats an order line from a name, a price, a quantity and a gift flag. Written with Any, every call compiles, including the one with all four arguments in the wrong order. Written with str, float, int and bool, the same wrong call fails while the checker scans the file. Nothing has to run.

Simple types have limits of their own. A function that transfers money between two accounts takes both account numbers as strings, so the checker accepts the call that swaps them: both sides have the same type. That example waits in section 3, beside its fix.

A simple type can also be the wrong claim outright. float holds approximate reals, and money is exact. The type checks, and the arithmetic drifts.

All three problems share one shape: the type accepts values the program never means. The rest of this page narrows that gap.

2. Aliases and units

A type alias gives a name to an existing type. The checker treats the alias and the original as the same type, so an alias documents intent and enforces nothing. To make the checker enforce the name, the type has to be distinct. Python spells that NewType. TypeScript reaches the same place with a brand: an intersection with a property that exists only in the type system. In both languages the distinct type costs nothing at run time.

The 1999 Mars Climate Orbiter was lost because one system produced pound-seconds and another read newton-seconds. The type system is the cheap place to catch that class of mistake.

Aliases are still useful, for naming. A long function type reads better under a short name, and one edit changes every signature that uses it. A named constant does the same for a magic number.

There is a limit worth knowing. A distinct type guards substitution, and arithmetic escapes it: the sum of two branded numbers comes back as a plain number in both languages. When quantities are added and multiplied, give them a small class with typed operations, and the units survive the arithmetic.

Strings have the same weakness. A status held as str accepts every string ever typed, including the misspelled ones. A literal type lists the values that exist, and the checker rejects the rest during its scan.

Literals also belong in parameters. A flag documented as "either text or binary" can state that in its type, and the rule moves from the docstring into the checker. The rejection cuts both ways: a variable typed as a plain string can no longer reach the parameter, because it could hold anything.

3. Domain types

Using raw strings and numbers for everything has a name: Scott Wlaschin calls it primitive obsession. The cure is a domain type, a type that carries a fact about the problem the program solves. An email address is a string that a specific check accepted. The pattern has three parts: a distinct type, one function that constructs it, and no other way to get one. Code that holds an EmailAddress can rely on the check without repeating it.

The same pattern retires the transfer bug from section 1. Give each kind of account its own type, and the swapped call stops compiling.

Domain types also describe states. A pending payment has no receipt. One class with an optional receipt field allows four combinations, and two of them describe payments that can never exist. One type per state allows the two that do, and the checker makes every reader handle both.

4. Parse, don't validate

Domain types raise a question: where do they come from? The outside world hands a program text. A command line is a list of strings. An environment variable is a string. An HTTP body is a string of JSON. A file is bytes. None of it carries a type, and something has to turn it into the objects the program works with.

Validating checks a value and passes it along unchanged. The knowledge that the check happened lives nowhere, so every reader checks again. Parsing checks a value and returns a different type. The result proves the check ran, the checker carries that proof to every caller, and the inner checks come out. Alexis King named the rule, parse, don't validate, and gave it a slogan worth keeping: write functions on the data you wish you had. Do the parsing once, at the edge of the system.

The command line first. argv arrives as strings: the user typed port=8080, and "8080" is text until something makes it a number. The before version keeps the settings as a dictionary of strings, so every function that needs the port converts and re-checks it. The after version has one function, parse_argv, that reads the strings once and returns a Config: a domain object whose port field is an int, guaranteed by its type. A bad command line fails right there, with a message, before the program does any work.

The network edge works the same way. A response body is a JSON string; json.loads and JSON.parse turn it into a shapeless dictionary, and the shape still has to be checked. Both ecosystems have a library for that step: pydantic in Python, zod in TypeScript. Declare the shape once, as a schema. The library checks the input against it and returns a real domain object, an Order with typed fields, or an error that names the field and the reason. The handler below never touches the dictionary: it goes from the raw body to an Order in one line, and every function after it works with the object.

After this section, a program has two zones. At the edge, raw input becomes domain types, and failures are handled where they can be reported. Inside, every function takes domain types, and the checker guarantees the garbage never gets that far.

5. Functions as values

A function has a type too: what it takes, and what it returns. Once that type is written down, functions can be passed around and checked like any other value. Leave the type open with Callable[..., int] or any, and the checker waves through key functions that crash at run time.

A function that takes or returns a function is a higher-order function. The useful ones wrap: retry, memoize, log. A wrapper is safe when it keeps the wrapped signature, and both languages can state that. Python spells it with type parameters, [**P, R]. TypeScript spells it with a generic argument tuple.

6. Pure functions

A function is pure when the same arguments always produce the same result and nothing else happens: no clock, no network, no global state. The signature offers a strong hint, because a function whose answer depends only on its parameters has to receive everything it needs.

The clock became a parameter, and the function became a table of facts a test can check. This pairs with section 4: parse at the edge, keep effects at the edge, and let the core be pure functions between domain types. The edge stays thin, and the core stays testable.

7. Composition and monads

Small pure functions become programs by composition: the output of one is the input of the next. Types make composition safe. A pipeline compiles only when the steps fit, so a step out of order is a compile error before it can become a production incident.

Real steps can fail. The plain spelling of failure returns None or null, and each caller stops and checks before continuing. It works, and every kind of failure collapses into the same empty answer. A Result keeps the pipeline shape with the failure inside it: it holds either a value or a reason, and and_then applies the next step to a value and passes a failure straight through. The chain reads like the happy path, and the first failure wins.

This shape has a name. A wrapper type with a way in (Ok), a way to transform the inside (map), and a way to chain steps that return the wrapper (and_then, also called flatMap or bind) is a monad. The standard ones cover the standard problems:

  • Option handles absence. x | None narrowing in Python and optional chaining in TypeScript play this role.
  • Result handles failure with a reason. You met it above.
  • List handles many answers at once. A comprehension and flatMap are its chaining step.
  • Promise handles answers that arrive later. then chains and flattens.
  • Writer carries a log beside the value, so the audit trail arrives with the answer.
  • IO describes an effect without performing it, so policies like retry become ordinary functions over descriptions.

Two of those you have used all along:

A Writer, hand-rolled: each step returns its result and its log line, and the chain concatenates the trails. The log becomes data the caller can assert on, attach to a response, or drop.

And an IO: wrap the computation instead of running it, and effects become values. A retry policy stops being a loop pasted into every network function and becomes one combinator that wraps any description. Nothing runs until the edge of the program says run.

A word of honesty before you rewrite a codebase around these. Hand-rolled monads are non-standard in Python and TypeScript, and most teams will read them as obstacles. Idiomatic code in these languages already has the specialised forms: None narrowing, exceptions at the edge, comprehensions, async/await. Reach for those first. The shape is still worth knowing, because those idioms are the monads, one per problem, and the shape tells you what a clean pipeline looks like even when you spell it natively.

And the definition you may have heard, "a monad is just a monoid in the category of endofunctors", is a real sentence from category theory and a running joke about explanations that explain nothing. Keep the working definition instead: a way in, a map, and a flattening chain.

8. Exercises

Each exercise starts from working, badly typed code. Rewrite it so the checker catches the defect described. Each block shows one solution behind a toggle, with the diff, and every solution passes the same CI checks as the rest of the page.

Exercise 1: make the typo impossible

One branch of the status function is dead because of a typo, and the checker cannot know. Make the typo a compile error, and make a forgotten status a compile error too.

Hint

Section 2: a literal type. Section 3: an exhaustive match with assert_never, or a switch with a never default.

Exercise 2: name the units and the flags

Two call sites disagree about the argument order, and both compile. Make the units distinct types and the flags named fields, so only one of the calls survives.

Hint

Section 2 for the units. For the flags, a frozen dataclass or an object type with named fields.

Exercise 3: parse the user once

A user arrives as JSON and travels as a loose dictionary, so every function re-checks the fields it reads. Parse once at the edge and delete the checks.

Hint

Section 4. Declare the shape with pydantic or zod, parse in summary, and let the field types travel.

Exercise 4: separate the currencies

An amount is a number, and its currency is a string beside it. The guard runs at run time. Move it into the types, so adding dollars to euros stops compiling.

Hint

In Python, one class per currency and a constrained type variable, [M: (Usd, Eur)]. In TypeScript, a generic currency parameter and NoInfer on the second argument.

Exercise 5: give each failure its reason

Three lookups can each fail, and every failure collapses into the same empty answer. Rewrite the chain with a Result so each failure carries its reason.

Hint

Section 7. Three small functions returning Result, and and_then to thread them.
