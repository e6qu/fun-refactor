The recipe language

A refactoring, written down

A recipe says what to find, what to do to it, and what must be true afterwards. It is reviewable, re-runnable, and it fails loudly.

Every command in this tool acts on one target. That is right for a person at a terminal and wrong for the work people actually have: "retire this flag, delete what it was guarding, and tidy the imports that leaves behind" is three commands in order, each depending on the last. Written as a shell loop the refusals scroll past, the ordering is implicit, and the thing you actually did is written down nowhere a reviewer can read. A recipe makes the plan the artifact; the diff is what it produces.

Generated  Every report and every diff below is what fr recipe actually did, captured by cargo test --test site_data. That test fails when the page and the tool disagree.

The shape of one

schema 1

recipe name {
  description "why this exists"

  requires symbol "USE_LEGACY_AUTH"     # refuse early if this is the wrong tree

  operation where predicate…  modifier…

  expect changed > 0 files
}

Layout is insignificant and statements are not terminated. A statement ends when the parser meets a token that can only begin a new one, which works because step keywords are reserved and no predicate shares a name with one — an invariant a test enforces rather than hopes for. That is what lets a where clause run across as many lines as it needs with no punctuation.

It is not a programming language. No loops, no arithmetic, no conditionals. The moment a recipe needs those it should be a program calling the CLI. And it does not extend what the tool can do: if a step could not be typed as an fr command, it is not a step.

The operations

StepTakesSelector
rename to "x"a namerequired

rewrite guard-clausethe transformationrequired — it chooses files
extract function at "…" as "…"a range and a namerejected — a range is not selectable
remove-flag "F" = falsethe flag and its valuerejected — it acts on the whole workspace
restructure go 'a($X)' => 'b($X)'a shape and a templaterejected — the pattern is the selector

“Rejected” means an error naming the operation and why, never a silent ignore. A grammar that reads operation , [selector] , {modifier} cannot say that rewrite needs a name or that remove-flag has no use for a where clause, so a signature table checks it immediately after the parse.

matches='log($X)'a structural shape — fr restructure. Needs lang= beside it

Each of the last five is an existing analysis rather than new machinery, and each runs only when a predicate asks for it: building a call graph over a large repository for a selector that says name="x" is work nobody asked for. matches= needs a lang= beside it because the same text parses into a different tree in every language, so there is no language-free answer to where a shape occurs.

A selector that matches nothing stops the recipe. Silently doing nothing is the failure this most wants to avoid, because it looks exactly like success. Write allow-empty when a step is genuinely conditional.

Refusals, transactions, expectations

on-refusal is stop by default — abandon the run, write nothing. report applies the rest and exits non-zero; allow applies the rest and exits zero, because a person decided these refusals were acceptable. There is deliberately no ignore: a refusal is always in the report, and the only question is what it costs.

A recipe is one transaction. Either every step's edits are written or none are, and each step sees the workspace as the previous step left it — which means re-indexing between them. Dry run is the default, as everywhere else here.

Five languages, five things it teaches

Writing one language as another

Not a refactoring — a translation, and a different promise. The signature is the contract; anything with no counterpart is carried into the output verbatim and counted.
